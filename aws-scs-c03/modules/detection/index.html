De los requisitos a las alertas (1.1.1 / 1.1.2)

Antes de activar nada conviene responder tres preguntas sobre la carga de trabajo, porque de ellas salen las fuentes de log, las métricas y el umbral de cada alerta. El examen plantea a menudo el escenario al revés —te da la alerta y pregunta qué falta— y el hilo del que hay que tirar es siempre este.

PreguntaQué determina
¿Qué activos hay y cuáles son sensibles?Qué recursos se monitorizan y con qué prioridad: no todo merece una alerta que despierte a alguien.
¿Qué eventos importan y qué marco de cumplimiento aplica?Qué fuentes se ingieren y cuánto se conservan. La retención sale del requisito, no del coste.
¿Quién responde y en cuánto tiempo?Si el destino es un panel, un correo o una remediación automática, y qué severidad justifica cada uno.

Con eso ya se puede elegir el mecanismo. Para estado del recurso —una instancia que no responde, un endpoint caído— la herramienta son los health checks y las alarmas de CloudWatch sobre una métrica, con su periodo y sus puntos de datos. Para cambios de configuración o de comportamiento —alguien abre un security group, GuardDuty ve tráfico a un dominio conocido— el camino es EventBridge sobre el evento, que dispara en segundos y no depende de que una métrica cruce un umbral.

Métrica o evento Una alarma de CloudWatch necesita una serie temporal; si lo que quieres vigilar ocurre una sola vez y no produce métrica —un PutBucketPolicy, un DeleteTrail— la respuesta es una regla de EventBridge, o un metric filter sobre el grupo de logs si de verdad necesitas contar apariciones.

GuardDuty vs Macie vs Config vs Security Hub (1.1.4)

Cuatro servicios que el examen confunde a propósito en las respuestas incorrectas. Cada uno responde una pregunta distinta.

ServicioPregunta que respondeCómo funciona
GuardDuty"¿Hay comportamiento anómalo o una amenaza activa?"ML + threat intelligence sobre CloudTrail, VPC Flow Logs, DNS logs, runtime monitoring — sin activar nada manualmente.
Macie"¿Dónde tengo datos sensibles (PII) expuestos o mal ubicados?"Descubrimiento y clasificación de contenido en S3 mediante ML y patrones gestionados/personalizados.
AWS Config"¿Mi configuración cumple la regla X?" (ej. cifrado activado)Evalúa el ESTADO de configuración de recursos contra reglas (Config Rules / Conformance Packs), con remediación automática opcional.
Security Hub"Dame TODO en un solo panel, con contexto de compliance"Agrega findings de los anteriores (+ terceros) y ejecuta sus propios checks contra CIS/PCI-DSS/AWS FSBP.
Tip de examen Si la pregunta describe contenido de DATOS ("números de tarjeta en un bucket") → Macie. Si describe COMPORTAMIENTO/RED ("llamada API desde una IP de Tor", "instancia minando criptomonedas") → GuardDuty. Si describe CONFIGURACIÓN ESTÁTICA de un recurso ("¿este bucket tiene versioning activado?") → Config. Si pide un PANEL ÚNICO o habla de "postura de seguridad" en general → Security Hub.

Automatizar evaluaciones regulares (1.1.5)

  • AWS Config Conformance Packs: paquete de reglas + remediaciones desplegado centralmente a nivel de organización/OU.
  • Security Hub: ejecuta sus checks de compliance de forma continua y automática, no puntual.
  • Systems Manager State Manager: aplica y mantiene un estado de configuración deseado en instancias (ej. "el agente de CloudWatch debe estar siempre corriendo"), corrigiendo desviaciones automáticamente.

Delegar GuardDuty y auto-incorporar las cuentas nuevas

# Desde la management account: delegar en la cuenta de seguridad.
aws guardduty enable-organization-admin-account \
  --admin-account-id 444455556666

# Desde la cuenta delegada: que toda cuenta nueva entre sola.
aws guardduty update-organization-configuration \
  --detector-id 12abc34d567e8fa901bc2d34e56789f0 \
  --auto-enable-organization-members ALL

Fuentes de log & arquitectura de logging (1.2.1 / 1.2.2)

Identificar QUÉ registrar es tan importante como CÓMO centralizarlo.

FuenteQué captura
CloudTrailLlamadas a la API (management events: quién hizo qué; data events opcionales: operaciones sobre objetos S3/funciones Lambda individuales).
CloudWatch LogsLogs de aplicación/sistema enviados por el CloudWatch Agent, Lambda, contenedores, etc.
VPC Flow LogsMetadatos de conexiones de red (ver detalle más abajo).
Route 53 Resolver query logsConsultas DNS resueltas desde dentro de la VPC.

Crear un organization trail centralizado vía CLI (desde la cuenta de gestión)

aws cloudtrail create-trail \
  --name "org-security-trail" \
  --s3-bucket-name "central-logging-account-cloudtrail" \
  --is-organization-trail \
  --is-multi-region-trail \
  --enable-log-file-validation
Ejemplo llano Imagina que tu cuenta de producción se ve comprometida y el atacante obtiene credenciales de administrador. Si el CloudTrail de esa cuenta escribe a un bucket S3 DE LA MISMA CUENTA, el atacante puede borrar el rastro de sus propias acciones (s3:DeleteObject sobre los logs). Si en cambio los logs viajan a una cuenta de logging separada donde ni siquiera el rol comprometido tiene s3:DeleteObject, la evidencia sobrevive intacta — la separación de cuentas no es burocracia, es una defensa activa.

Bucket policy que impide borrar o alterar los logs entregados

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PermitirEntregaDeCloudTrail",
      "Effect": "Allow",
      "Principal": { "Service": "cloudtrail.amazonaws.com" },
      "Action": "s3:PutObject",
      "Resource": "arn:aws:s3:::central-security-logs-111122223333/AWSLogs/o-abc123/*",
      "Condition": {
        "StringEquals": { "s3:x-amz-acl": "bucket-owner-full-control" }
      }
    },
    {
      "Sid": "NadieBorraLosLogs",
      "Effect": "Deny",
      "Principal": "*",
      "Action": ["s3:DeleteObject", "s3:DeleteObjectVersion", "s3:PutBucketPolicy"],
      "Resource": [
        "arn:aws:s3:::central-security-logs-111122223333",
        "arn:aws:s3:::central-security-logs-111122223333/*"
      ]
    }
  ]
}

Crear un organization trail que capture también data events de S3

aws cloudtrail create-trail \
  --name org-security-trail \
  --s3-bucket-name central-security-logs-111122223333 \
  --is-organization-trail \
  --is-multi-region-trail \
  --kms-key-id alias/cloudtrail-cmk

# Los data events NO se capturan por defecto: hay que pedirlos.
aws cloudtrail put-event-selectors \
  --trail-name org-security-trail \
  --advanced-event-selectors '[
    {
      "Name": "Lecturas y escrituras de objetos S3",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["Data"] },
        { "Field": "resources.type", "Equals": ["AWS::S3::Object"] }
      ]
    }
  ]'

aws cloudtrail start-logging --name org-security-trail

Amazon Security Lake & OCSF (1.2.3)

  • Ingesta, normaliza (a OCSF) y particiona logs de múltiples cuentas/fuentes AWS y de terceros compatibles en un data lake gestionado (sobre S3, en tu propia cuenta).
  • Elimina el trabajo de ETL manual que necesitarías para poder correlacionar formatos de log completamente distintos con una sola consulta.
  • Se integra de forma nativa con Athena, OpenSearch y SIEMs de terceros que ya hablan OCSF.

Consulta Athena: buscar llamadas denegadas en CloudTrail

SELECT eventtime,
       useridentity.arn      AS principal,
       eventsource,
       eventname,
       errorcode,
       sourceipaddress
FROM   cloudtrail_logs
WHERE  errorcode IN ('AccessDenied', 'UnauthorizedOperation')
  AND  eventtime > '2026-08-01T00:00:00Z'
ORDER  BY eventtime DESC
LIMIT  100;

VPC Flow Logs & Route 53 Resolver logs (1.2.6)

Distinción clave VPC Flow Logs = QUIÉN se conectó a QUIÉN (metadatos IP, no contenido). Route 53 Resolver logs = QUÉ DOMINIO se resolvió antes de esa conexión. Un ataque típico de exfiltración vía DNS tunneling puede pasar desapercibido en Flow Logs (el tráfico DNS parece normal en volumen) pero se detecta claramente en los Resolver logs analizando la ENTROPÍA/longitud inusual de las subconsultas.

Troubleshooting de logging roto (1.3.1 / 1.3.2)

Patrón de pregunta muy repetido: "el log group está vacío, ¿por qué?" — casi siempre son las mismas dos causas.

SíntomaCausas más comunes
CloudWatch Agent corriendo pero sin logsConfiguración del agente mal apuntada (rutas/log group incorrectos) o permisos IAM insuficientes en el Instance Profile.
Lambda se ejecuta pero sin logsExecution role sin logs:CreateLogStream/logs:PutLogEvents (falta la managed policy AWSLambdaBasicExecutionRole).
API Gateway sin detalle de request/responseFalta activar explícitamente "data trace logging" a nivel de stage (el execution logging por defecto no incluye el body).
CloudFront sin logs recientesConfundir Standard logs (diferidos, a S3) con Real-time logs (Kinesis, segundos) — revisar cuál está realmente configurado.

Comprobar por qué un trail dejó de entregar

# ¿Sigue registrando, y falló la última entrega?
aws cloudtrail get-trail-status --name org-security-trail

# Salida relevante:
# "IsLogging": false                      -> el logging está parado
# "LatestDeliveryError": "AccessDenied"   -> la bucket policy o la KMS key bloquean
# "LatestDeliveryAttemptTime": "..."      -> cuándo lo intentó por última vez

# Si el error es AccessDenied sobre KMS, revisar que la key policy
# permita a cloudtrail.amazonaws.com la acción kms:GenerateDataKey*

Trampas típicas del examen

Los errores que más se repiten en este dominio. Si vas justo de tiempo antes del examen, repasa solo esto y el quiz.

Management events no son data events CloudTrail registra por defecto solo management events (plano de control: CreateBucket, PutBucketPolicy). Quién descargó un objeto concreto es un data event, está desactivado por defecto y hay que habilitarlo. Si el enunciado dice "no vemos quién accedió al objeto", la respuesta casi siempre es habilitar data events.
GuardDuty no necesita que actives sus fuentes GuardDuty lee CloudTrail, VPC Flow Logs y DNS logs de forma independiente, mediante un service-linked role. No hace falta habilitar esos logs ni pagarlos para que GuardDuty funcione. Cualquier opción que diga "primero habilita VPC Flow Logs para que GuardDuty pueda analizarlos" es un distractor.
Los cuatro servicios que siempre se confunden GuardDuty detecta amenazas y comportamiento malicioso. Inspector evalúa vulnerabilidades (CVEs) en instancias, contenedores y Lambda. Macie descubre datos sensibles en S3. Config evalúa el estado de configuración de los recursos. Ninguno hace el trabajo del otro, y el examen los intercambia constantemente.
Multi-cuenta y multi-Región son ejes distintos En Security Hub, GuardDuty o Config, el delegated administrator resuelve la vista multi-cuenta y la agregación de Regiones resuelve la multi-Región. Son dos configuraciones separadas: si la pregunta pide ambas cosas, hacen falta las dos respuestas.
Los logs no aparecen retroactivamente Ampliar la retención, crear un trail nuevo o habilitar una fuente no genera los eventos que no se capturaron en su momento. Si el incidente ya ocurrió y el logging estaba mal configurado, esa evidencia no existe. Cualquier opción que prometa recuperar eventos pasados es falsa.
VPC Flow Logs no ven el contenido Registran metadatos de la conexión (IPs, puertos, protocolo, bytes, accept/reject), nunca el payload. Si la pregunta necesita saber qué se transfirió, Flow Logs no basta. Además hay tráfico que no capturan, como el dirigido al servidor DNS de Amazon o a 169.254.169.254.

Las tareas y skills que AWS publica para el dominio 1 en la guía del examen. El 16% de las preguntas del examen sale de aquí.

Tarea 1.1 — Diseñar e implementar la monitorización y las alertas de una cuenta u organización

  • 1.1.1 Analizar las cargas de trabajo para determinar qué hay que monitorizar

  • 1.1.3 Agregar eventos de seguridad y de monitorización
  • 1.1.4 Crear métricas, alertas y paneles que detecten datos y eventos anómalos (GuardDuty, Security Lake, Security Hub, Macie)
  • 1.1.5 Crear y mantener automatizaciones de evaluación e investigación periódicas (conformance packs de Config, Security Hub, State Manager)

Tarea 1.2 — Diseñar e implementar soluciones de logging

  • 1.2.1 Identificar las fuentes de log a ingerir y almacenar según los requisitos
  • 1.2.2 Configurar el logging de servicios y aplicaciones (trail de organización, cuenta dedicada de logs, agente de CloudWatch Logs)
  • 1.2.3 Implementar almacenamiento y lagos de datos de logs (Security Lake) e integrarlos con herramientas de terceros
  • 1.2.4 Analizar logs con servicios de AWS (CloudWatch Logs Insights, Athena, findings de Security Hub)
  • 1.2.5 Normalizar, parsear y correlacionar logs (OpenSearch Service, Lambda, Managed Grafana)
  • 1.2.6 Elegir las fuentes de log según el diseño de red y las amenazas (VPC Flow Logs, transit gateway flow logs, logs de Route 53 Resolver)

Tarea 1.3 — Diagnosticar problemas de monitorización, logging y alertas de seguridad

  • 1.3.1 Analizar funcionalidad, permisos y configuración de los recursos (logging de Lambda, de API Gateway, health checks, logs de CloudFront)
  • 1.3.2 Corregir configuraciones erróneas (agente de CloudWatch, logs que no llegan)
