Security solutions for applications and data

The domain that closes the exam and the one most often underestimated. Three tasks with one thread running through them: data is not protected where it sits, but where it is used. In Microsoft 365 and Copilot, in your applications' code, and in the databases underneath them. This is where the exam puts its newest content: the Copilot controls and the security of the data AI consumes.

What this exam takes for granted

Four mechanisms this domain uses constantly without explaining them, and on which several answers depend that otherwise look arbitrary.

Envelope encryption: why revoking a key makes data unreadable instantly

No service encrypts terabytes with your key directly. Each block of data is encrypted with a data key generated on the fly, and that key is in turn encrypted with a key encryption key and stored alongside the data. This is called envelope encryption.

The key you control — the customer-managed one, in Key Vault — is the outer one, the wrapper. That is why withdrawing the service's access to it leaves the data unreadable immediately and without rewriting anything: the data keys are still there, but nobody can unwrap them. And it is why rotating that key is cheap, while rotating the inner one would mean re-encrypting everything.

How a label's protection travels outside your tenant

A sensitivity label with encryption does not mark the file: it encrypts it and embeds a usage policy inside — who may open it and what they may do: read, edit, print, forward — along with a reference to the service holding the key.

When somebody opens it, the application contacts that service, authenticates, and only then receives the key and the rights it is entitled to. Hence the two consequences the exam asks about: the protection stays alive outside your organisation, because the check happens at open time and not at send time; and it can be revoked afterwards, because the file is useless if the service stops handing over the key.

And hence the difference from DLP too DLP is evaluated in the channel — the mail server, the SharePoint site, the endpoint agent — at the moment the data tries to leave. A label is evaluated in the file every time it is opened. That is why one prevents the exit and the other survives the exit, and why so many requirements need both.

What a SAS actually is, and why one of them cannot be revoked

A shared access signature is a string carrying the permissions, the resource, the validity window and a signature. Storage consults no database: it recomputes the signature with the key and, if it matches, lets the request through. There is no list of issued SAS anywhere.

That explains the whole problem. A SAS signed with the account key is only invalidated by changing that key, which takes down everything else using it. A user delegation SAS is signed with a temporary key Entra ID hands to a specific identity: revoking that delegation — or that identity's permissions — kills every SAS hanging off it, without touching the account.

Workload identity federation: the token exchange

When an external system — a pipeline, somebody else's cluster — needs into Azure, the alternative to a secret is this: you register in Entra ID that you trust a specific issuer and a specific subject within it — this organisation, this repository, this branch. The external system obtains a token signed by its own issuer, presents it to Entra ID, and Entra ID checks the signature and the match and exchanges it for one of its own.

Nothing is stored anywhere: the trust is in the relationship, not in a value. That is why the exam prefers it to any secret however well guarded, and why the detail of scoping the branch or the environment matters: without it, any branch in the repository deploys to production.

Envelope encryption: why revoking the key cuts access

The data is never re-encrypted on revocation: what breaks is the chain that allows unwrapping the key that opens it.

The data, not the container: the thread of this domain

The earlier domains protected places: the machine, the network, the cluster. This one protects data moving between places, which is why its answers are almost never an infrastructure control. A stem describing an email leaving with a payroll spreadsheet is not solved with a firewall, and one describing Copilot showing a document the user should not see is not solved with conditional access.

The reflex for this domain Always ask which verb the stem is asking for: discover, label, stop it leaving, retain, prove or encrypt. Each verb has its capability, and the two-answer questions usually combine exactly two of them.

Measuring the posture of the productivity workloads (4.1.1)

The metric is Microsoft Secure Score in the Defender portal, and here it is the right one: it measures tenant configuration — Exchange, SharePoint, Teams, Entra ID, managed devices — with improvement actions prioritised by impact and effort. Watch for the confusion that already came up in domain 3: it is not the Defender for Cloud secure score, which measures cloud resources, and it is not a compliance report.

What the exam wants you to say about Secure Score That it is for prioritising and tracking progress, and that comparison with similar organisations is context, not a goal. Chasing 100% is the wrong answer: some actions do not apply to your environment and are documented as such.

Intune inside the design (4.1.3)

Intune already appeared in domain 3 as endpoint management; here it comes in as the provider of the signal the Microsoft 365 data access decisions depend on. What gets specified: configuration policies, compliance policies, and app protection policies for what is unmanaged. And the piece that ties it together: app context — conditional access requires a compliant device, and only then does the application hand over the data.

Label or DLP They get confused because they sound alike. The label travels with the file and keeps protecting it once it has left; DLP watches the channel and stops it leaving. Security and compliance controls in Copilot for Microsoft 365 (4.1.5)

New syllabus content and highly askable, because the misconception is nearly universal. Copilot creates no new permissions: it answers with what the user could already open. If it shows something it should not, the problem is not Copilot — it is that this user already had access and nobody had noticed.

An option proposing "a policy stopping Copilot reading X" is usually the distractor: the control lives at the source, not in the assistant.

Evaluating the posture of an application portfolio (4.2.1)

You do not audit application by application: you inventory and classify. Which applications exist, who maintains them, what data they touch, whether they are business critical — and from that comes where to invest. Pieces the platform gives you: Defender for Cloud Apps discovery for what is used without permission, the Entra ID application inventory for what is registered, and Defender for APIs for what is published.

Standards and practices for the development process (4.2.4)

Here what is protected is not the application but the chain that builds it, which is a target in its own right. What gets specified: identity and least privilege for the pipeline, with federated workload identity instead of credentials stored in the CI system; protected branches with mandatory review; environments with approval for production; secrets kept out of the repository and detected if they appear; and ephemeral build agents.

The pipeline's credential An application secret held in the CI system to deploy into Azure is the pattern the exam wants replaced: workload identity federation, where the pipeline presents a token from its own provider and Azure exchanges it for access, with no secret to rotate or steal.

Workload identities (4.2.6)

A workload identity belongs to a service, not to a person, and the design turns on two decisions: that it holds no secret and that it is governed.

  • Managed identity — system or user assigned — for any Azure resource consuming another Azure service. There is no credential: the platform handles it.
  • Workload identity federation for what lives outside Azure — a GitHub pipeline, somebody else's Kubernetes cluster: it presents a token from its issuer and Azure accepts it, with no stored secret.
  • App registration with a secret or certificate only when there is no alternative, with rotation and the secret in Key Vault.
  • Governance: workload identities get reviewed too — owner, granted permissions, actual use — and conditional access can be applied to them.

Azure Web Application Firewall (4.2.8)

The WAF lives on Front Door (global) or on Application Gateway (regional), and what the exam asks is not how to turn it on but how to roll it out without breaking the application: you start in detection mode with the managed rule set, review the false positives and tune with exclusions and custom rules, and only then move to prevention mode. It is the same measure, tune, enforce pattern as in Azure Policy.

A WAF that can be bypassed protects nothing If the origin still accepts direct requests, the attacker skips the edge. The design always includes locking the origin down so it only accepts traffic from the edge service.

Discovering and classifying the data (4.3.1)

You cannot protect what you do not know exists, and this is the first piece of any data design in this exam. Microsoft Purview covers both halves: the data map scans and catalogues sources — Azure Storage, databases, other clouds, on-premises — and classification recognises the content with sensitive information types, trainable classifiers and exact data match where precision matters.

Prioritising the mitigation of threats to data (4.3.2)

Prioritisation comes from crossing two axes: the data's sensitivity — what classification says — and its exposure — who can reach it. A store with regulated data and public access comes first; one with internal data and restricted access can wait. Defender for Cloud supports this with sensitive data discovery across resources and with the attack paths that end at them.

Sensitivity by exposure If a stem hands you a list of findings and asks where to start, the criterion is not technical severity: it is where sensitive data is within reach of somebody who should not have it.

At rest, in transit and in use The exam distinguishes all three states and the third is the forgotten one. If the stem says "not even Microsoft should be able to read it while it is processed", no customer-managed key solves it: that is confidential computing.

Securing the data AI workloads consume (4.3.4)

New content, and the angle differs from domain 3: there you protected the AI service, here the data going into and out of it. The four design questions:

  • What data feeds the model — the grounding corpus is classified and labelled first, and it inherits the source's permissions. A model querying an overshared store spreads that oversharing faster.
  • What leaves in the prompt — the request travels to a service; classification and DLP must cover that channel too.
  • What gets stored — traces, logs and conversations are data: retention, residency and who can read them are explicit decisions.
  • What the output inherits — content generated from labelled material carries the label forward, so the protection is not lost by rewriting it.

Masking is not encryption Dynamic data masking hides the value in the response, but the data stays in clear in the database and whoever holds direct query permission sees it. If the requirement is that not even the database administrator can see it, that is Always Encrypted.

Securing data in Azure Storage (4.3.6)

  • No account keys: access with Entra ID and data roles; if delegated access is needed, a user delegation SAS, which expires and can be revoked, rather than a SAS signed with the account key.
  • No public access on the container, and a private endpoint for the account.
  • Encryption with a customer key where the regulation asks, and infrastructure encryption if a double layer is required.
  • Immutability with legal hold or time-based retention policies where the data cannot be modified or deleted.
  • Soft delete and versioning to survive accidental or malicious deletion.

Common traps in this domain

Configuring Copilot instead of fixing permissions Copilot creates no access: it exposes what was already there. The prerequisite work is reducing oversharing and labelling the content.
Confusing labels with DLP The label protects the file wherever it goes; DLP stops it leaving. Many requirements need both.
Dynamic masking treated as encryption It hides the value in the response, not in the database. For the administrator not to see it either, Always Encrypted.
A SAS signed with the account key It cannot be revoked without rotating the key and taking everyone down. The answer is a user delegation SAS.
A secret in the continuous integration system The design the exam expects is workload identity federation: no secret to rotate or steal.
WAF in prevention from day one Same as with Azure Policy: detection first to measure the false positives, prevention afterwards.
