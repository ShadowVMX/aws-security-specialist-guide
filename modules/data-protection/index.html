Antes de KMS, hay que tener claros tres ejes que el examen combina constantemente.

Envelope encryption — el concepto que más se pregunta

KMS casi nunca cifra tus datos directamente: cifra una "data key" que a su vez cifra tus datos. Haz clic en cada paso.

Haz clic en cualquier paso del diagrama para ver la explicación detallada.

Envelope encryption: KMS nunca ve tus datos, solo la data key

Si vienes de Azure Azure Key Vault también soporta un patrón de envelope encryption (usando WrapKey/UnwrapKey), conceptualmente idéntico. La diferencia organizativa: Azure Key Vault es UN servicio que guarda claves, secretos Y certificados juntos. AWS reparte esa misma funcionalidad en tres servicios distintos: KMS (claves de cifrado), Secrets Manager (credenciales/secretos) y ACM (certificados) — cada uno con su propia consola, pricing y API. Mentalmente, "Key Vault" ≈ "KMS + Secrets Manager + ACM" combinados.

Cifrado inter-recurso (5.1.3 — nuevo en SCS-C03)

Skill añadido en la versión actual del examen: cifrado del tráfico ENTRE nodos de un mismo servicio distribuido, no solo cliente↔servicio.

  • Amazon EMR: "in-transit encryption" en la Security Configuration del cluster cifra el tráfico entre nodos (incluido el shuffle de Spark) con TLS.
  • Amazon EKS: cifrado inter-nodo típicamente vía service mesh (App Mesh, Istio) o CNI con soporte de cifrado — no es automático por defecto en el plano de datos.
  • Amazon SageMaker AI: "inter-container traffic encryption" cifra la comunicación entre los contenedores de un job de entrenamiento distribuido.
  • Nitro encryption: en instancias EC2 sobre el Nitro System, el tráfico entre instancias Nitro (y la memoria local) se cifra automáticamente a nivel de infraestructura, sin configuración del cliente.
Ejemplo llano Cifrar tu bucket S3 con SSE-KMS protege los datos QUIETOS en disco. Pero si tienes un cluster EMR de 20 nodos procesando esos datos y haciendo shuffle de resultados intermedios ENTRE esos 20 nodos, ese tráfico interno viaja sin cifrar salvo que actives explícitamente "in-transit encryption" en la Security Configuration — es un punto que se olvida fácilmente porque "ya tengo todo cifrado" (en reposo) no significa "todo el tráfico está cifrado" (en tránsito, incluso interno).

Integridad de datos (5.2.2)

  • S3 Object Lock: WORM (Write Once Read Many) a nivel de objeto. Modo Governance (bypasseable con permiso especial) vs Compliance (inmutable, ni root puede saltárselo).
  • S3 Glacier Vault Lock: política de retención que, una vez confirmada ("locked"), es permanente e inmutable — útil para cumplimiento normativo verificable (SEC 17a-4, etc.).
  • S3 Versioning (+ MFA Delete): conserva todas las versiones de un objeto; MFA Delete exige un código MFA adicional para eliminar versiones o desactivar el versioning.
  • AWS Signer: firma digital de código (Lambda, contenedores, firmware IoT) para verificar que no ha sido alterado.
  • File validation de CloudTrail: cada archivo de log incluye un hash firmado digitalmente para detectar manipulación posterior de los logs.

Configurar Object Lock en modo Compliance vía CLI

aws s3api put-object-retention \
  --bucket "regulated-records" \
  --key "contracts/2026-report.pdf" \
  --retention '{"Mode":"COMPLIANCE","RetainUntilDate":"2033-01-01T00:00:00Z"}'
Ejemplo llano Governance mode es como un "no tocar salvo emergencia con autorización especial" — un administrador con el permiso s3:BypassGovernanceRetention puede saltárselo si de verdad hace falta. Compliance mode es un candado sin llave: ni siquiera el dueño de la cuenta AWS puede abrirlo antes de la fecha fijada. Úsalo solo cuando la regulación lo exige de verdad, porque no hay vuelta atrás.

Lifecycle & retención (5.2.3)

  • S3 Lifecycle policies: reglas de transition (cambiar de clase de almacenamiento por antigüedad) y expiration (eliminar automáticamente tras N días).
  • Amazon EFS Lifecycle Management: mueve archivos poco accedidos automáticamente a EFS Infrequent Access.
  • Amazon FSx for Lustre backup policies: snapshots automáticos programados del sistema de archivos.

La pieza SIN equivalente directo y muy preguntada es AWS Backup Vault Lock: Azure Backup tiene "immutable vaults", conceptualmente similar, pero en el examen AWS lo relevante es el matiz Governance-like vs Compliance-like en el propio Vault Lock (modo compliance = irreversible ni por soporte de AWS).

AWS Secrets Manager (5.3.1)

Gestión y rotación de credenciales y secretos — la pieza que más distingue a Secrets Manager de simplemente "guardar un valor cifrado".

  • Rotación automática nativa con funciones Lambda integradas para RDS, Aurora, Redshift y DocumentDB: rota la credencial Y la actualiza en la base de datos en el mismo ciclo, sin downtime si se configura bien (rotación de dos usuarios alternados).
  • Para otros secretos (API keys de terceros, tokens), puedes escribir tu propia función Lambda de rotación siguiendo las 4 fases estándar: createSecret, setSecret, testSecret, finishSecret.
  • Integración nativa con IAM (resource policies del secreto) y KMS (cifrado en reposo).

Rotar un secreto de RDS cada 30 días vía CLI

aws secretsmanager rotate-secret \
  --secret-id "prod/rds/app-db" \
  --rotation-lambda-arn "arn:aws:lambda:eu-west-1:111122223333:function:SecretsManagerRDSRotation" \
  --rotation-rules '{"AutomaticallyAfterDays": 30}'
Si vienes de Azure Azure Key Vault Secrets cubre el almacenamiento cifrado, pero no trae rotación automática integrada para bases de datos como Secrets Manager — en Azure sueles necesitar Event Grid + Azure Functions personalizadas para replicar ese flujo. Es una diferencia real de "features incluidas", no solo de nombres.

Imported key material & External Key Store (5.3.2 / 5.3.3)

Ver también el árbol de decisión de arriba. Aquí el matiz que más se pregunta: las diferencias prácticas frente a una key generada por AWS.

Generada por AWSMaterial importado (BYOK)
Rotación automáticaSí (opcional, anual)No — hay que re-importar manualmente
Expiración configurableNoSí, opcional (o "no expirar nunca")
Origen del materialGenerado dentro del HSM de AWSGenerado por ti, importado vía envoltura pública RSA
Si se elimina el materialN/ALa key queda inutilizable de inmediato (útil como "kill switch")
Si vienes de Azure Azure Key Vault también soporta BYOK (importar claves generadas fuera, incluso protegidas por HSM con un paquete de transferencia validado). El concepto es equivalente. Donde AWS va un paso más allá es con External Key Store (XKS): el material NUNCA entra en AWS en ningún momento, ni siquiera durante la importación — Azure no tiene un equivalente directo tan estricto (lo más cercano sería una integración BYOK gestionada completamente fuera vía Managed HSM con tu propio control de acceso, pero el modelo de "proxy externo por cada operación criptográfica" de XKS es más específico de AWS).

Masking de datos sensibles (5.3.4 — nuevo en SCS-C03)

Enmascarar datos sensibles que aparecen donde no deberían, sin bloquear el flujo de logs/mensajes por completo.

  • CloudWatch Logs data protection policies: detectan tipos de datos sensibles (tarjetas de crédito, SSN, claves de acceso de AWS, o detectores personalizados con regex) y enmascaran el valor en las vistas/consultas. Solo principals con logs:Unmask ven el valor real.
  • Amazon SNS message data protection: misma idea aplicada a mensajes SNS — detecta y enmascara (o bloquea) datos sensibles antes de que el mensaje llegue a los suscriptores.

Política de protección de datos en un log group (fragmento)

{
  "Name": "mask-pii-policy",
  "Statement": [
    {
      "Sid": "audit-and-mask-credit-cards",
      "DataIdentifier": ["arn:aws:dataprotection::aws:data-identifier/CreditCardNumber"],
      "Operation": {
        "Audit": { "FindingsDestination": {} },
        "Deidentify": { "MaskConfig": {} }
      }
    }
  ]
}

Certificados & claves multi-Region (5.3.5)

ServicioPara qué
ACM (público)Certificados TLS gratuitos, de confianza pública, con renovación automática. Para dominios públicos verificables.
AWS Private CATu propia jerarquía de CA privada: certificados internos para mTLS entre microservicios, IoT, IAM Roles Anywhere. Solo de confianza donde distribuyas el certificado raíz. Coste por CA activa.
KMS Multi-Region keysRéplicas que comparten el MISMO material criptográfico entre regiones — cifra en una región, descifra en otra sin re-cifrar. Distinto de crear keys idénticas de forma independiente en cada región (esas tendrían material distinto e incompatible).
Cuidado si vienes de Azure Azure Key Vault es un recurso regional: para tener alta disponibilidad multi-región de tus claves, replicas manualmente el Key Vault completo (o usas Managed HSM con su propio mecanismo). AWS KMS Multi-Region keys son conceptualmente distintas: no son "el mismo servicio replicado", son réplicas de UNA clave con material compartido gestionadas de forma nativa por KMS (ReplicateKey), con Key IDs distintos por región pero criptográficamente intercambiables. No asumas que es "lo mismo con otro nombre".
