Rate-based rule en WAF vía CLI (bloquea tras 2000 requests/5min por IP)

  --name "rate-limit-login" \
  --scope REGIONAL \
  --capacity 50 \
  --rules '[{
    "Name": "block-high-rate",
    "Priority": 0,
    "Action": {"Block": {}},
    "Statement": {"RateBasedStatement": {"Limit": 2000, "AggregateKeyType": "IP"}},
    "VisibilityConfig": {"SampledRequestsEnabled": true, "CloudWatchMetricsEnabled": true, "MetricName": "rateLimitLogin"}
  }]'

Reglas de edge avanzadas & OCSF (3.1.3 / 3.1.4)

  • Geolocation / rate limiting / client fingerprinting: WAF combina condiciones (país, volumen, huella del cliente vía JA3/JA4 fingerprinting) para bloquear patrones de bot sofisticados que rotan de IP.
  • Reglas de terceros: AWS Marketplace ofrece managed rule groups de proveedores de seguridad especializados (además de las AWS Managed Rules).
  • OCSF (Open Cybersecurity Schema Framework): esquema abierto que normaliza eventos de seguridad de AWS y terceros al mismo formato — usado nativamente por Amazon Security Lake para poder correlacionar sin escribir un parser por cada fuente.

AMIs & imágenes de contenedor hardened (3.2.1)

EC2 Image Builder automatiza un pipeline: imagen base → componentes de hardening/config → parches → tests → AMI/imagen de contenedor publicada.

Si vienes de Azure Azure Image Builder es prácticamente el mismo concepto con el mismo nombre: pipeline gestionado para construir imágenes VM hardened y reproducibles a partir de una imagen base + customizaciones. Uno de los mapeos más directos de todo el examen.

Instance profiles, service roles & execution roles (3.2.2)

TipoSe usa en
Instance ProfileEC2 — contenedor que asocia un IAM Role a la instancia; el SDK obtiene credenciales automáticamente del Instance Metadata Service (IMDS).
Service RoleUn servicio de AWS (ej. Config, CodePipeline) asume este rol para actuar en tu nombre sobre otros recursos.
Execution RoleLambda/ECS/Fargate — permisos que tiene el CÓDIGO en ejecución, distinto del rol que despliega la función/tarea.
Cuidado con IMDSv1 vs IMDSv2 IMDSv1 (basado en simples peticiones HTTP GET) es vulnerable a SSRF: una petición HTTP maliciosa reenviada por la app puede robar las credenciales del Instance Profile. IMDSv2 exige un token de sesión obtenido con PUT, que la mayoría de bibliotecas SSRF no reenvían — fuérzalo con HttpTokens=required en la configuración de metadata de la instancia (o vía Declarative Policy a nivel de organización).

Acceso administrativo seguro (3.2.5)

Si vienes de Azure Systems Manager Session Manager ↔ Azure Bastion: ambos dan acceso de shell sin abrir puertos entrantes (22/3389) ni exponer IP pública, con sesiones auditadas centralmente. La diferencia: Azure Bastion es un recurso de red que despliegas en la VNet (con coste fijo por hora); Session Manager es un agente + servicio gestionado sin recurso de red que aprovisionar, y además funciona sobre instancias híbridas (on-premises) registradas en Systems Manager.

Iniciar una sesión sin SSH ni puerto abierto

aws ssm start-session --target i-0123456789abcdef0

Seguridad en el pipeline & guardrails GenAI (3.2.6 / 3.2.7)

  • Amazon CodeGuru Security: análisis estático (SAST) de código fuente en el pipeline — vulnerabilidades y secretos hardcodeados antes de desplegar.
  • Amazon Q Developer: sugerencias de remediación asistidas por IA integradas en el IDE/pipeline.
Ejemplo llano — nuevo en SCS-C03 Si tu aplicación expone un chatbot basado en un LLM (ej. vía Bedrock) a usuarios finales, el OWASP Top 10 for LLM Applications cataloga riesgos específicos que no existen en apps tradicionales: prompt injection (un usuario manipula el prompt para saltarse las instrucciones del sistema), fuga de datos sensibles en las respuestas del modelo, o envenenamiento de los datos usados para fine-tuning/RAG. Implementar guardrails (ej. Amazon Bedrock Guardrails) para filtrar entradas/salidas es la respuesta típica del examen ante este escenario.

Security Groups vs Network ACLs (3.3.1)

Security GroupNetwork ACL
NivelENI / instanciaSubnet
EstadoStateful (el retorno se permite solo)Stateless (hay que permitir ida y vuelta)
ReglasSolo AllowAllow y Deny, evaluadas en orden numérico
AlcanceSe evalúan TODAS las reglas (no hay orden)Se detiene en la primera regla que haga match
Cuidado si vienes de Azure — esto es distinto Azure tiene UN solo constructo, el Network Security Group (NSG), que puedes asociar a una subnet O a una NIC, y que SÍ soporta reglas explícitas de Deny con prioridad numérica — es decir, un NSG se parece un poco a la mezcla de Security Group + NACL de AWS. En AWS, en cambio, son DOS mecanismos separados con comportamientos distintos (stateful vs stateless) que se aplican SIEMPRE juntos (primero NACL de la subnet, luego SG de la instancia). No asumas que "ya tengo NACL configurada = no necesito Security Group" ni al revés: en AWS ambas capas actúan simultáneamente.

Elegir conectividad híbrida (Skills 3.3.2 / 3.3.3)

Si vienes de Azure Direct Connect ↔ Azure ExpressRoute (ExpressRoute Direct también soporta MACsec — mapeo muy directo). Site-to-Site VPN ↔ Azure VPN Gateway (S2S). Sin equivalente 1:1 sencillo: Verified Access se parece más a Entra Private Access que a cualquier producto de red tradicional de Azure.

Segmentación de red & AWS Network Firewall (3.3.4 / 3.3.5)

  • North/south: tráfico que cruza el perímetro (Internet ↔ VPC). East/west: tráfico interno entre cargas de trabajo — aislarlo reduce el blast radius si un componente se compromete.
  • Subnets aisladas (sin ruta a Internet, ni siquiera vía NAT) para las cargas más sensibles (ej. bases de datos).
  • AWS Network Firewall: inspección de capa 3-7 con estado, reglas de dominio (FQDN) y firmas tipo IDS/IPS (Suricata) — más avanzado que SG/NACL para tráfico de tránsito.
  • Detectar accesos no intencionados: Amazon Inspector (Network Reachability) y VPC Network Access Analyzer modelan toda la cadena SG+NACL+route tables para encontrar rutas alcanzables que no deberían existir.
Si vienes de Azure AWS Network Firewall ↔ Azure Firewall: ambos son firewalls gestionados de capa 3-7 con reglas de dominio, pensados para tráfico centralizado de tránsito (a menudo detrás de un Transit Gateway / Virtual WAN respectivamente).
