Tipos de políticas en IAM

Todo en IAM gira en torno a documentos de política en JSON evaluados sobre tres preguntas: ¿quién (Principal)?, ¿qué acción?, ¿sobre qué recurso?

TipoSe adjunta aNotas clave para el examen
Identity-based (managed)Users, Groups, RolesAWS managed (predefinidas por AWS) o Customer managed (creadas por ti). Reutilizables y versionadas.
Identity-based (inline)Un único User, Group o RoleRelación 1:1, no reutilizable. Útil solo para casos muy puntuales; mala práctica a escala.
Resource-basedEl propio recurso (S3, KMS, SQS, SNS, Lambda, Secrets Manager…)Único tipo que puede especificar un Principal de OTRA cuenta directamente, habilitando acceso cross-account sin AssumeRole.
Permission boundaryUsers o RolesNo otorga permisos; define el techo máximo. El efectivo es la intersección.
Organizations SCPCuentas / OUsGuardrail que limita identidades DENTRO de la organización. Nunca otorga permisos por sí sola.
Organizations RCPCuentas / OUsGuardrail que limita el acceso a los RECURSOS, incluyendo principals externos/anónimos. Complementa a SCP.
Session policySe pasa al hacer AssumeRole/GetFederationTokenIgual que un boundary: solo puede acotar, nunca ampliar, los permisos del rol.
Tip de examen Si una pregunta describe "quiero limitar lo máximo que un desarrollador puede hacer aunque su rol tenga permisos amplios" → permission boundary. Si describe "quiero un guardrail que aplique a toda una OU sin importar qué política tenga cada usuario" → SCP (identidades) o RCP (recursos).

Orden de evaluación de políticas IAM (actualizado con RCP, 2024+)

Ejemplo paso a paso Ana (developer) intenta borrar un objeto del bucket finance-reports con s3:DeleteObject.

1. Llega la petición: Principal = Ana, Acción = s3:DeleteObject, Recurso = el objeto.
2. ¿Deny explícito? La bucket policy de finance-reports tiene un Deny explícito para s3:DeleteObject salvo para el rol FinanceAdmin. Ana no es ese rol → DENY inmediato, fin de la evaluación. No importa que su identity policy le diera s3:*: el Deny explícito de un tercer documento (la bucket policy) gana igualmente.

Si esa Deny no existiera, seguiríamos: ¿la SCP de su OU permite s3:DeleteObject? ¿Tiene Ana un Allow explícito en su identity policy? ¿Su permission boundary también lo permite? Solo si las CUATRO preguntas dan verde, se ejecuta el borrado.

IAM Roles & AWS STS

Un Role es una identidad con políticas de permisos que NO tiene credenciales permanentes: se "asume" y genera credenciales temporales vía AWS STS (Security Token Service).

API de STSCuándo usarla
AssumeRoleCaso general: un IAM User o Role (misma cuenta o cross-account) asume otro rol.
AssumeRoleWithSAMLFederación empresarial con IdP SAML 2.0 (ADFS, Okta, Azure AD/Entra ID) sin usuarios IAM.
AssumeRoleWithWebIdentityApps móviles/web con login OIDC (Google, Facebook, Amazon Cognito). En producción, mejor vía Cognito Identity Pools.
GetFederationTokenFederación legacy para dar acceso limitado a usuarios sin identidad IAM, usando las credenciales del usuario que llama.
GetSessionTokenCredenciales temporales para un IAM User existente, típicamente para forzar MFA en llamadas a la API.
DecodeAuthorizationMessageDescifra el mensaje de error codificado cuando una llamada fue denegada (troubleshooting).

Trust policy (assume role policy document) de un rol

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "sts:ExternalId": "unique-partner-id-2026" }
      }
    }
  ]
}

Asumir el rol vía AWS CLI

aws sts assume-role \
  --role-arn "arn:aws:iam::444455556666:role/CrossAccountAuditRole" \
  --role-session-name "juan-audit-session" \
  --external-id "unique-partner-id-2026" \
  --duration-seconds 3600
Cuidado sts:ExternalId es obligatorio cuando un tercero (proveedor SaaS, auditor externo) asume tu rol, para mitigar el confused deputy problem. Combínalo siempre con aws:SourceArn/aws:SourceAccount cuando quien asume es un servicio de AWS actuando en nombre de otro cliente.

Amazon S3 presigned URLs — la otra forma de dar acceso temporal

El exam guide de SCS-C03 agrupa STS y los presigned URLs de S3 bajo el mismo skill: "mecanismos para emitir credenciales temporales". No son lo mismo, y el examen distingue cuándo usar cada uno:

  • Un presigned URL no genera credenciales nuevas: firma una URL con las credenciales de quien la genera (usuario o rol), delegando acceso a UNA acción sobre UN objeto concreto durante un tiempo limitado (hasta 7 días con SigV4 y credenciales de IAM Role, o hasta 12h si se firma con las credenciales temporales de un rol).
  • Ideal para que un cliente sin credenciales de AWS (un navegador, una app externa) suba o descargue UN objeto S3 puntual, sin exponerle nunca access keys ni necesitar que asuma un rol.
  • Si el que genera la URL pierde el permiso subyacente (se revoca su rol/policy) antes de que expire, la URL deja de funcionar — sigue evaluándose contra IAM en cada uso.

Generar una presigned URL vía CLI (expira en 300s)

aws s3 presign s3://reports-bucket/2026/audit-final.pdf --expires-in 300

Acceso cross-account & confused deputy

El patrón más preguntado del examen: un usuario en la Cuenta A necesita operar recursos en la Cuenta B.

Haz clic en cualquier paso del diagrama para ver la explicación detallada.

Flujo de AssumeRole cross-account (requiere permiso de salida Y trust policy de entrada)

Ejemplo: por qué existe ExternalId Contratas a "DataSync Corp" (SaaS de terceros) para hacer backups de tu bucket S3. Les das el ARN de un rol en tu cuenta con una trust policy que confía en la Cuenta AWS de DataSync Corp. Problema: DataSync Corp tiene cientos de clientes, y su trust policy genérica podría permitir que asuman ese rol usando las mismas credenciales de su cuenta. Si otro cliente de DataSync Corp (malicioso o por error de configuración de la propia DataSync Corp) logra que el servicio asuma TU rol en vez del suyo, accede a tus datos sin que tú se lo hayas dado a él directamente — ese es el "confused deputy" (DataSync Corp es el "diputado confundido"). Al exigir un sts:ExternalId único que solo tú y DataSync Corp conocéis, tu trust policy solo confía en la combinación exacta cuenta+ExternalId, cerrando ese hueco.
Si vienes de Azure Lo más parecido a esto es Azure Lighthouse: permite a un tenant de gestión (ej. un MSP) operar recursos dentro de tu tenant sin cambiar de contexto. La diferencia importante para el examen: en Azure Lighthouse la delegación es persistente y visible directamente en el portal del tenant gestor (no hay un "assume" explícito en cada operación); en AWS, el acceso cross-account es siempre una llamada explícita a sts:AssumeRole que genera credenciales temporales con caducidad — un modelo más parecido, de hecho, a pedir un token para un Service Principal con permisos delegados en tu tenant vía Azure AD.

IAM Identity Center

Sucesor de AWS SSO. Es la forma recomendada por AWS de gestionar acceso humano multi-cuenta en 2026, por encima de crear IAM Users individuales.

  • Permission Sets: plantillas de permisos (managed o customer policies + permission boundaries) definidas una vez y asignadas a cuentas/grupos. Identity Center provisiona automáticamente los IAM Roles subyacentes en cada cuenta.
  • Fuente de identidad: puede usar el directorio interno de Identity Center, o federar con un IdP externo (Okta, Azure AD/Entra ID, Google Workspace, Ping) vía SAML/SCIM para sincronizar usuarios y grupos automáticamente.
  • Attribute-based access control (ABAC) integrado: Identity Center puede pasar atributos del usuario (departamento, coste center) como session tags al asumir el permission set.
  • Sustituye el patrón antiguo de "un IAM User por persona + credenciales de larga duración" — reduce drásticamente el riesgo de access keys filtradas.

Amazon Cognito & AWS Directory Service

Skill 4.1.1 agrupa explícitamente IAM Identity Center, Cognito y MFA como las tres piezas para autenticar humanos, aplicaciones y sistemas. Identity Center cubre acceso humano a cuentas AWS; Cognito cubre usuarios finales de tus propias aplicaciones.

ComponentePara qué sirveDetalle clave
Cognito User PoolsDirectorio de usuarios de TU aplicación (sign-up/sign-in, MFA, verificación de email/SMS)Devuelve JSON Web Tokens (ID, Access, Refresh) tras el login. No da credenciales de AWS por sí solo.
Cognito Identity PoolsIntercambia una identidad ya autenticada (de un User Pool, Google, SAML...) por credenciales temporales de AWSEs la capa recomendada sobre AssumeRoleWithWebIdentity — gestiona el intercambio de forma segura sin exponer secretos en el cliente.
AWS Directory ServiceDirectorios Active Directory gestionados para autenticación empresarial on-prem/híbrida3 modos: AWS Managed Microsoft AD (AD real, gestionado, soporta trusts), AD Connector (proxy hacia un AD on-premises existente, sin replicar datos) y Simple AD (compatible con Samba, funcionalidad reducida).
Cómo distinguirlos en el examen "Usuarios finales de mi app web/móvil hacen login" → Cognito. "Empleados de la empresa acceden a la consola/CLI de AWS con su cuenta corporativa" → IAM Identity Center (posiblemente federado contra AD vía Directory Service). "Quiero exponer un AD on-premises existente a servicios AWS sin migrarlo" → AD Connector.
Si vienes de Azure Cognito User Pools es el equivalente a Azure AD B2C / Microsoft Entra External ID: gestión de identidad para clientes/usuarios finales de TU aplicación, separada del tenant corporativo. Cognito Identity Pools no tiene un análogo tan directo en Azure — la forma habitual allí de dar acceso a recursos a un usuario externo autenticado es a través de un token validado por tu propio backend, que luego usa SU PROPIA identidad (Managed Identity o Service Principal) para tocar los recursos, en vez de "cambiar" el token del usuario final por credenciales de la nube como hace Cognito Identity Pools.

IAM Roles Anywhere

Extiende los roles de IAM a cargas de trabajo que corren FUERA de AWS: servidores on-premises, otros proveedores cloud, dispositivos edge.

  • Requiere una CA privada de confianza (ACM Private CA u otra CA registrada como trust anchor) que emite certificados X.509 a cada servidor/workload.
  • El workload presenta su certificado al endpoint de Roles Anywhere, que lo valida y lo intercambia por credenciales temporales de AWS vía STS — mismo principio que AssumeRoleWithSAML pero con certificados en vez de aserciones SAML.
  • Elimina la necesidad de access keys de larga duración distribuidas manualmente en servidores fuera de AWS.

Troubleshooting de autenticación

Skill 4.1.3, explícito en el exam guide: saber dónde mirar cuando alguien "no puede iniciar sesión" es tan examinable como configurarlo.

  • CloudTrail: primer sitio para ver el evento AssumeRole/ConsoleLogin fallido y el motivo exacto (errorCode, errorMessage) — incluye intentos denegados por trust policy, MFA ausente o SCP.
  • Cognito: revisar los logs de Advanced Security Features y los eventos de User Pool (fallos de verificación, throttling, triggers Lambda que bloquean el login).
  • IAM Identity Center permission sets: un permission set editado no se re-provisiona automáticamente en las cuentas — hay que reaplicarlo, causa común de "le quité el permiso pero sigue teniendo acceso" o al revés.
  • AWS Directory Service: problemas de conectividad de red (Security Groups, NACLs) entre la VPC y los DCs on-premises son la causa más común de fallos con AD Connector.

Permission boundaries, session policies & IAM paths

Ambos mecanismos comparten la misma regla: nunca amplían permisos, solo los acotan mediante intersección con la identity/resource policy.

Permission boundary — un desarrollador solo puede tocar S3 y DynamoDB, nunca IAM

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:*", "dynamodb:*"],
      "Resource": "*"
    },
    {
      "Effect": "Deny",
      "Action": ["iam:*"],
      "Resource": "*"
    }
  ]
}
Caso de uso típico en el examen "Permitir que los desarrolladores creen sus propios roles IAM, pero sin que puedan auto-otorgarse permisos de administrador" → adjuntar un permission boundary obligatorio en la política que les permite iam:CreateRole, usando la condición iam:PermissionsBoundary.
Ejemplo llano — sin equivalente directo en Azure Imagina que le das a un becario el rol Contributor sobre un resource group en Azure. Si mañana alguien (por error o de forma malintencionada) le asigna además el rol Owner, no hay ningún mecanismo nativo de Azure RBAC que diga "da igual qué rol le asignen después, este becario JAMÁS podrá superar el techo X". Cada asignación de rol es independiente. En AWS sí existe ese techo estructural: si el becario tiene un permission boundary que solo permite S3/DynamoDB, aunque alguien le adjunte por error AdministratorAccess como identity policy, sus permisos reales siguen acotados a S3/DynamoDB — el boundary manda siempre. Es el motivo por el que el examen lo pregunta tanto: es un concepto genuinamente distinto a "asignar un rol con más o menos permisos".

IAM paths — organizar y acotar identidades por prefijo

Todo User y Role IAM tiene un path opcional (por defecto /) que forma parte de su ARN: arn:aws:iam::111122223333:role/division_abc/subdivision_xyz/mi-rol. Skill 4.2.1 lo lista junto a resource policies y trust policies como mecanismo de control de autorización.

  • Sirve para agrupar identidades por equipo/proyecto y luego escribir políticas de administración que solo permitan gestionar roles/usuarios bajo un path concreto, usando condiciones como iam:ResourceTag o restringiendo el Resource con wildcard sobre el path (arn:aws:iam::*:role/division_abc/*).
  • Un caso de examen típico: delegar a un equipo de plataforma la creación de roles solo dentro de su propio path, combinado con un permission boundary obligatorio — doble control de mínimo privilegio.

ABAC & RBAC — control de acceso basado en atributos o en roles

RBAC (role-based) es el modelo clásico: una política por rol/función de negocio. ABAC (attribute-based) compara tags del principal con tags del recurso — escala sin reescribir políticas cuando el número de recursos crece.

Política ABAC: solo acceso a recursos del mismo "project" que el usuario

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["ec2:StartInstances", "ec2:StopInstances"],
      "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/project": "${aws:PrincipalTag/project}"
        }
      }
    }
  ]
}
  • Requiere activar tag-based access control y etiquetar consistentemente tanto identidades (vía Identity Center session tags o tags del IAM Role) como recursos.
  • Ideal para entornos multi-equipo donde el número de recursos crece constantemente — evita mantener cientos de políticas específicas.
Si vienes de Azure Azure también tiene ABAC, pero con un alcance mucho más limitado: en Azure, las condiciones de rol basadas en atributos solo se soportan sobre Blob Storage y algunos tipos de recursos concretos (ej. "solo lectura de blobs con tag Project=Finance"). En AWS, ABAC funciona de forma transversal en la mayoría de servicios (EC2, S3, KMS, Secrets Manager...) porque se implementa directamente como condiciones dentro de cualquier política IAM, no como una capacidad aparte de un servicio concreto.

Amazon Verified Permissions

Todo lo anterior (identity-based, resource-based, ABAC) autoriza acceso a la API de AWS. Amazon Verified Permissions resuelve un problema distinto: autorización fina dentro de TUS propias aplicaciones (¿puede este usuario ver este documento? ¿puede editar este pedido?), fuera del control plane de AWS.

  • Motor de autorización gestionado basado en Cedar, el lenguaje de políticas open-source de AWS: políticas legibles tipo permit(principal == User::"ana", action == Action::"viewDocument", resource in Folder::"finance").
  • Se integra en el código de la aplicación vía SDK/API (IsAuthorized) — la app le pregunta a Verified Permissions en cada request si esa acción concreta está permitida, en vez de tener la lógica de autorización hardcodeada.
  • Soporta RBAC y ABAC dentro del propio modelo Cedar, y se integra de forma nativa con Cognito para usar los grupos/atributos del usuario autenticado.
Cómo distinguirlo en el examen Si la pregunta habla de permisos sobre llamadas a la API de AWS (S3, EC2, IAM...) → política IAM clásica. Si habla de lógica de negocio dentro de tu aplicación ("qué documentos puede ver este usuario de mi SaaS") → Amazon Verified Permissions.

Guardrails de organización: SCP, RCP y Declarative Policies

MecanismoQué limitaAplica a
Service Control Policy (SCP)El máximo permiso que las IDENTIDADES de la cuenta pueden usar (aunque IAM diga que sí, si la SCP no lo permite, se deniega)Cuentas / OUs dentro de la Organization
Resource Control Policy (RCP)Quién puede acceder a los RECURSOS de la cuenta, incluyendo principals externos y anónimos — cierra el hueco que las SCP no cubrenRecursos soportados (S3, STS, KMS, SQS, Secrets Manager…) en cuentas / OUs
Declarative PoliciesFuerza un estado de configuración deseado para atributos específicos de servicio (ej. exigir IMDSv2, bloquear puertos públicos por defecto) — no es allow/deny de API, es "así debe estar configurado siempre"Atributos concretos soportados, a nivel de cuenta / OU
Cómo distinguirlos en el examen Si la pregunta dice "queremos que ninguna cuenta pueda desactivar el cifrado por defecto de EBS, pase lo que pase" → Declarative Policy. Si dice "queremos que nadie en la organización pueda usar la región eu-west-1" → SCP. Si dice "queremos que ningún bucket S3 de la organización pueda compartirse con cuentas fuera de la organización, ni con condiciones de política a nivel de bucket" → RCP.
Cuidado si vienes de Azure — trampa de nombres "Service Control Policy" suena a Azure Policy, pero NO son lo mismo. Azure Policy audita/fuerza principalmente la configuración de los recursos que se crean (ej. "todo storage account debe tener HTTPS obligatorio") — eso se parece mucho más a las Declarative Policies de AWS o a las Config Rules. Una SCP, en cambio, es un techo de permisos de IAM (qué acciones puede ejecutar una identidad), y su equivalente más cercano en Azure son las deny assignments (usadas en Blueprints/Landing Zones), que bloquean acciones a nivel de Management Group sin importar qué rol RBAC tenga asignado el usuario. Si en el examen ves "SCP", piensa en permisos denegados, no en compliance de configuración.

IAM Access Analyzer & Policy Simulator

Skill 4.2.4 nombra explícitamente ambas herramientas para analizar fallos de autorización — resuelven preguntas distintas.

  • External access findings: detecta recursos (buckets, roles, KMS keys, snapshots...) accesibles desde fuera de tu "zona de confianza" (cuenta u organización). Se define un analizador con el scope deseado.
  • Unused access findings: identifica roles no usados, permisos no ejercidos y access keys inactivas — soporte directo al principio de mínimo privilegio.
  • Policy validation & custom policy checks: valida sintaxis y buenas prácticas mientras escribes políticas en la consola/CLI, e incluso permite comprobar si un cambio de política introduce nuevo acceso externo antes de desplegarlo (CheckNoNewAccess / CheckAccessNotGranted).

Listar hallazgos de acceso externo vía CLI

aws accessanalyzer list-findings-v2 \
  --analyzer-arn "arn:aws:access-analyzer:eu-west-1:111122223333:analyzer/org-analyzer" \
  --filter '{"findingType": {"eq": ["ExternalAccess"]}}'

IAM Policy Simulator

Herramienta distinta y complementaria: en vez de analizar la postura real de la cuenta (como Access Analyzer), simula si una política concreta permitiría o denegaría una acción específica ANTES de aplicar ningún cambio real — sin generar llamadas reales a la API ni dejar rastro en CloudTrail.

Root user & MFA

  • Nunca uses el root para tareas del día a día. Aplica MFA (preferiblemente FIDO2/hardware security key) y no generes access keys para el root.
  • Centralized Root Access Management (Organizations, 2023+): permite gestionar de forma centralizada las credenciales root de las cuentas miembro e invocar un set acotado de acciones privilegiadas de root sin repetir el proceso de recuperación de contraseña cuenta por cuenta.
  • Condición aws:MultiFactorAuthPresent para exigir MFA en llamadas a la API; combínala con aws:MultiFactorAuthAge para limitar la antigüedad máxima de la sesión MFA.
  • IAM credential report (cuenta completa) vs Access Advisor (por usuario/rol, qué servicios se usaron y cuándo) — ambos clave para auditorías periódicas.

Exigir MFA para cualquier acción sobre EC2

{
  "Effect": "Deny",
  "Action": "ec2:*",
  "Resource": "*",
  "Condition": {
    "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
  }
}
Si vienes de Azure Aquí el salto es al revés de lo habitual: en Azure, Conditional Access es un motor centralizado que evalúa señales (ubicación, riesgo del usuario, cumplimiento del dispositivo...) y decide en un solo sitio si exige MFA, bloquea el acceso o fuerza un dispositivo gestionado, aplicable de forma uniforme a todo el tenant. AWS no tiene un motor equivalente centralizado: la condición aws:MultiFactorAuthPresent hay que añadirla política por política (o de forma centralizada vía SCP/RCP, pero sigue siendo una condición de "sí/no", no un motor de riesgo adaptativo). Si en el examen una pregunta suena a "políticas de acceso condicional adaptativas basadas en riesgo", probablemente la respuesta correcta combine varios servicios (IAM + GuardDuty + Identity Center), no un único servicio equivalente a Conditional Access.
