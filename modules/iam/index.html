Tipos de políticas en IAM

Todo en IAM gira en torno a documentos de política en JSON evaluados sobre tres preguntas: ¿quién (Principal)?, ¿qué acción?, ¿sobre qué recurso?

TipoSe adjunta aNotas clave para el examen
Identity-based (managed)Users, Groups, RolesAWS managed (predefinidas por AWS) o Customer managed (creadas por ti). Reutilizables y versionadas.
Identity-based (inline)Un único User, Group o RoleRelación 1:1, no reutilizable. Útil solo para casos muy puntuales; mala práctica a escala.
Resource-basedEl propio recurso (S3, KMS, SQS, SNS, Lambda, Secrets Manager…)Único tipo que puede especificar un Principal de OTRA cuenta directamente, habilitando acceso cross-account sin AssumeRole.
Permission boundaryUsers o RolesNo otorga permisos; define el techo máximo. El efectivo es la intersección.
Organizations SCPCuentas / OUsGuardrail que limita identidades DENTRO de la organización. Nunca otorga permisos por sí sola.
Organizations RCPCuentas / OUsGuardrail que limita el acceso a los RECURSOS, incluyendo principals externos/anónimos. Complementa a SCP.
Session policySe pasa al hacer AssumeRole/GetFederationTokenIgual que un boundary: solo puede acotar, nunca ampliar, los permisos del rol.
Tip de examen Si una pregunta describe "quiero limitar lo máximo que un desarrollador puede hacer aunque su rol tenga permisos amplios" → permission boundary. Si describe "quiero un guardrail que aplique a toda una OU sin importar qué política tenga cada usuario" → SCP (identidades) o RCP (recursos).

IAM Roles & AWS STS

Un Role es una identidad con políticas de permisos que NO tiene credenciales permanentes: se "asume" y genera credenciales temporales vía AWS STS (Security Token Service).

API de STSCuándo usarla
AssumeRoleCaso general: un IAM User o Role (misma cuenta o cross-account) asume otro rol.
AssumeRoleWithSAMLFederación empresarial con IdP SAML 2.0 (ADFS, Okta, Azure AD/Entra ID) sin usuarios IAM.
AssumeRoleWithWebIdentityApps móviles/web con login OIDC (Google, Facebook, Amazon Cognito). En producción, mejor vía Cognito Identity Pools.
GetFederationTokenFederación legacy para dar acceso limitado a usuarios sin identidad IAM, usando las credenciales del usuario que llama.
GetSessionTokenCredenciales temporales para un IAM User existente, típicamente para forzar MFA en llamadas a la API.
DecodeAuthorizationMessageDescifra el mensaje de error codificado cuando una llamada fue denegada (troubleshooting).

Trust policy (assume role policy document) de un rol

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "sts:ExternalId": "unique-partner-id-2026" }
      }
    }
  ]
}

Asumir el rol vía AWS CLI

aws sts assume-role \
  --role-arn "arn:aws:iam::444455556666:role/CrossAccountAuditRole" \
  --role-session-name "juan-audit-session" \
  --external-id "unique-partner-id-2026" \
  --duration-seconds 3600
Cuidado sts:ExternalId es obligatorio cuando un tercero (proveedor SaaS, auditor externo) asume tu rol, para mitigar el confused deputy problem. Combínalo siempre con aws:SourceArn/aws:SourceAccount cuando quien asume es un servicio de AWS actuando en nombre de otro cliente.

IAM Identity Center

Sucesor de AWS SSO. Es la forma recomendada por AWS de gestionar acceso humano multi-cuenta en 2026, por encima de crear IAM Users individuales.

  • Permission Sets: plantillas de permisos (managed o customer policies + permission boundaries) definidas una vez y asignadas a cuentas/grupos. Identity Center provisiona automáticamente los IAM Roles subyacentes en cada cuenta.
  • Fuente de identidad: puede usar el directorio interno de Identity Center, o federar con un IdP externo (Okta, Azure AD/Entra ID, Google Workspace, Ping) vía SAML/SCIM para sincronizar usuarios y grupos automáticamente.
  • Attribute-based access control (ABAC) integrado: Identity Center puede pasar atributos del usuario (departamento, coste center) como session tags al asumir el permission set.
  • Sustituye el patrón antiguo de "un IAM User por persona + credenciales de larga duración" — reduce drásticamente el riesgo de access keys filtradas.

IAM Roles Anywhere

Extiende los roles de IAM a cargas de trabajo que corren FUERA de AWS: servidores on-premises, otros proveedores cloud, dispositivos edge.

  • Requiere una CA privada de confianza (ACM Private CA u otra CA registrada como trust anchor) que emite certificados X.509 a cada servidor/workload.
  • El workload presenta su certificado al endpoint de Roles Anywhere, que lo valida y lo intercambia por credenciales temporales de AWS vía STS — mismo principio que AssumeRoleWithSAML pero con certificados en vez de aserciones SAML.
  • Elimina la necesidad de access keys de larga duración distribuidas manualmente en servidores fuera de AWS.

Permission boundaries & session policies

Ambos mecanismos comparten la misma regla: nunca amplían permisos, solo los acotan mediante intersección con la identity/resource policy.

Permission boundary — un desarrollador solo puede tocar S3 y DynamoDB, nunca IAM

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:*", "dynamodb:*"],
      "Resource": "*"
    },
    {
      "Effect": "Deny",
      "Action": ["iam:*"],
      "Resource": "*"
    }
  ]
}
Caso de uso típico en el examen "Permitir que los desarrolladores creen sus propios roles IAM, pero sin que puedan auto-otorgarse permisos de administrador" → adjuntar un permission boundary obligatorio en la política que les permite iam:CreateRole, usando la condición iam:PermissionsBoundary.

ABAC — Control de acceso basado en atributos

En vez de escribir una política por recurso (RBAC clásico), ABAC compara tags del principal con tags del recurso — escala sin reescribir políticas.

Política ABAC: solo acceso a recursos del mismo "project" que el usuario

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["ec2:StartInstances", "ec2:StopInstances"],
      "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/project": "${aws:PrincipalTag/project}"
        }
      }
    }
  ]
}
  • Requiere activar tag-based access control y etiquetar consistentemente tanto identidades (vía Identity Center session tags o tags del IAM Role) como recursos.
  • Ideal para entornos multi-equipo donde el número de recursos crece constantemente — evita mantener cientos de políticas específicas.

Guardrails de organización: SCP, RCP y Declarative Policies

MecanismoQué limitaAplica a
Service Control Policy (SCP)El máximo permiso que las IDENTIDADES de la cuenta pueden usar (aunque IAM diga que sí, si la SCP no lo permite, se deniega)Cuentas / OUs dentro de la Organization
Resource Control Policy (RCP)Quién puede acceder a los RECURSOS de la cuenta, incluyendo principals externos y anónimos — cierra el hueco que las SCP no cubrenRecursos soportados (S3, STS, KMS, SQS, Secrets Manager…) en cuentas / OUs
Declarative PoliciesFuerza un estado de configuración deseado para atributos específicos de servicio (ej. exigir IMDSv2, bloquear puertos públicos por defecto) — no es allow/deny de API, es "así debe estar configurado siempre"Atributos concretos soportados, a nivel de cuenta / OU
Cómo distinguirlos en el examen Si la pregunta dice "queremos que ninguna cuenta pueda desactivar el cifrado por defecto de EBS, pase lo que pase" → Declarative Policy. Si dice "queremos que nadie en la organización pueda usar la región eu-west-1" → SCP. Si dice "queremos que ningún bucket S3 de la organización pueda compartirse con cuentas fuera de la organización, ni con condiciones de política a nivel de bucket" → RCP.

IAM Access Analyzer

Tres capacidades distintas bajo el mismo servicio — el examen las pregunta por separado.

  • External access findings: detecta recursos (buckets, roles, KMS keys, snapshots...) accesibles desde fuera de tu "zona de confianza" (cuenta u organización). Se define un analizador con el scope deseado.
  • Unused access findings: identifica roles no usados, permisos no ejercidos y access keys inactivas — soporte directo al principio de mínimo privilegio.
  • Policy validation & custom policy checks: valida sintaxis y buenas prácticas mientras escribes políticas en la consola/CLI, e incluso permite comprobar si un cambio de política introduce nuevo acceso externo antes de desplegarlo (CheckNoNewAccess / CheckAccessNotGranted).

Listar hallazgos de acceso externo vía CLI

aws accessanalyzer list-findings-v2 \
  --analyzer-arn "arn:aws:access-analyzer:eu-west-1:111122223333:analyzer/org-analyzer" \
  --filter '{"findingType": {"eq": ["ExternalAccess"]}}'

Root user & MFA

  • Nunca uses el root para tareas del día a día. Aplica MFA (preferiblemente FIDO2/hardware security key) y no generes access keys para el root.
  • Centralized Root Access Management (Organizations, 2023+): permite gestionar de forma centralizada las credenciales root de las cuentas miembro e invocar un set acotado de acciones privilegiadas de root sin repetir el proceso de recuperación de contraseña cuenta por cuenta.
  • Condición aws:MultiFactorAuthPresent para exigir MFA en llamadas a la API; combínala con aws:MultiFactorAuthAge para limitar la antigüedad máxima de la sesión MFA.
  • IAM credential report (cuenta completa) vs Access Advisor (por usuario/rol, qué servicios se usaron y cuándo) — ambos clave para auditorías periódicas.

Exigir MFA para cualquier acción sobre EC2

{
  "Effect": "Deny",
  "Action": "ec2:*",
  "Resource": "*",
  "Condition": {
    "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
  }
}

Data perimeter

Concepto transversal muy presente en el examen 2026: garantizar que los datos nunca salgan de tu organización, incluso con credenciales válidas comprometidas.

Recurso¿Qué recursos son de confianza?RCP/SCP con aws:ResourceOrgID, resource policies restrictivas
Red¿Desde qué red se accede?VPC endpoint policies + aws:SourceVpce / aws:SourceIp
