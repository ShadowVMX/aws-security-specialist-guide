Los 4 tipos de política de organización (6.1.3)

SCP y RCP ya se cubrieron en profundidad en el módulo de IAM. Aquí el repaso rápido más los dos que faltaban.

TipoControla
Service Control Policy (SCP)Techo de PERMISOS de identidad — qué acciones de API puede hacer una identidad de la cuenta.
Resource Control Policy (RCP)Quién puede acceder a los RECURSOS, incluidos principals externos/anónimos.
Declarative PolicyFuerza un estado de CONFIGURACIÓN concreto (ej. IMDSv2 obligatorio) — no es allow/deny de API.
AI services opt-out policyControla si los servicios de IA de AWS pueden usar el contenido de tus cuentas para entrenar/mejorar sus modelos.

RCP que cierra el acceso a recursos desde fuera de la organización

{
  "Version": "2012-10-17",
  "Statement": [
    {

      "Effect": "Deny",
      "Principal": "*",

      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": { "aws:PrincipalOrgID": "o-abc123" },
        "BoolIfExists": { "aws:PrincipalIsAWSService": "false" }

  ]

Delegated administrator (6.1.4)

Ejemplo llano Piensa en la cuenta de management como la caja fuerte del banco: existe, es crítica, pero nadie debería estar entrando y saliendo de ella todos los días. Designar la cuenta "Audit" como delegated administrator de GuardDuty/Security Hub/Access Analyzer es como darle al equipo de seguridad las llaves de la sala de vigilancia (ven todo, actúan sobre todo lo relacionado con seguridad) sin darles las llaves de la caja fuerte en sí.

Root user: MFA, break-glass & gestión centralizada (6.1.5)

  • Break-glass procedure: proceso documentado y auditado de acceso de EMERGENCIA a root (MFA hardware bajo custodia controlada), nunca usado para operación normal.
  • Centralized root access management: permite a la cuenta de management invocar ciertas acciones root en cuentas miembro sin necesitar recuperar contraseñas individualmente, reduciendo el número de credenciales root realmente utilizables.
  • MFA obligatorio en TODAS las cuentas root, verificable de forma centralizada.
Si vienes de Azure "Break-glass" es prácticamente el mismo término y concepto que las cuentas de acceso de emergencia (emergency access accounts) de Microsoft Entra ID: cuentas excluidas de Conditional Access, con credenciales guardadas físicamente, monitorizadas con alertas si se usan alguna vez. Uno de los mapeos más directos (hasta en el nombre coloquial) de todo el examen.

Retirar credenciales root y actuar solo cuando hace falta

# Habilitar la gestión centralizada del acceso root en la organización.
aws organizations enable-aws-service-access \
  --service-principal iam.amazonaws.com

aws iam enable-organizations-root-credentials-management

# A partir de aquí, una tarea que exige root se hace con una sesión acotada
# por una TaskPolicy administrada por AWS — no con credenciales permanentes.
aws sts assume-root \
  --target-principal 111122223333 \
  --task-policy-arn arn:aws:iam::aws:policy/root-task/S3UnlockBucketPolicy

HerramientaPara qué
CloudFormation StackSetsDespliega/actualiza el MISMO stack en cientos de cuentas/regiones centralizadamente; integrable con Organizations para nuevas cuentas automáticamente.

Desplegar un StackSet a toda una OU (integrado con Organizations)

  --stack-set-name "baseline-security-config" \
  --template-url "https://s3.eu-west-1.amazonaws.com/templates/baseline.yaml" \
  --permission-model SERVICE_MANAGED \
  --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false

Estrategia de tagging (6.2.2)

No es solo FinOps: es la base de ABAC, conformance packs condicionales, y respuesta rápida en incidentes ("¿qué es producción?", "¿quién es el owner?").

Exigir etiquetas de verdad: la SCP que acompaña a la tag policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SinClasificacionNoSeCrea",
      "Effect": "Deny",
      "Action": ["ec2:RunInstances", "rds:CreateDBInstance"],
      "Resource": "*",
      "Condition": {
        "Null": { "aws:RequestTag/DataClassification": "true" }
      }
    }
  ]
}

AWS Firewall Manager (6.2.3)

Aplica y MANTIENE políticas de WAF, Shield Advanced, Security Groups y Network Firewall de forma centralizada en toda la organización — incluso sobre cuentas y recursos que se creen en el futuro, sin intervención manual repetida.

Si vienes de Azure AWS Firewall Manager ↔ Azure Firewall Manager: mapeo casi literal hasta en el nombre. Ambos centralizan políticas de firewall/WAF a escala de Management Group/Organization.

Compartir recursos entre cuentas (6.2.4)

ServicioComparte
AWS Resource Access Manager (RAM)Recursos concretos (subnets de una VPC compartida, Transit Gateway, reglas de Firewall Manager) directamente entre cuentas, sin duplicarlos.
AWS Service CatalogPlantillas de IaC PRE-APROBADAS como "productos" autoservicio, dando autonomía a los equipos sin ceder permisos amplios de creación de recursos.
Si vienes de Azure AWS RAM se parece a compartir una VNet vía Azure Lighthouse / delegated resource management, aunque el caso de uso más común de RAM (compartir subnets entre cuentas, "shared VPC") se parece más al patrón de hub-spoke con VNet peering gestionado centralmente que a Lighthouse en sí — no fuerces la comparación con Lighthouse más allá de "delegación de gestión entre tenants/cuentas".

Config aggregators & remediación automática (6.3.1)

Un Config Aggregator consolida el estado de compliance de múltiples cuentas/regiones en una vista única. Patrón estándar de respuesta:

Config detecta → EventBridge → SNS (notifica) + Systems Manager Automation (remedia)

aws configservice put-remediation-configurations \
  --remediation-configurations '[{
    "ConfigRuleName": "s3-bucket-public-read-prohibited",
    "TargetType": "SSM_DOCUMENT",
    "TargetId": "AWSConfigRemediation-RemoveS3BucketPublicReadAccess",
    "Automatic": true,
    "MaximumAutomaticAttempts": 3
  }]'

Agregador de Config para toda la organización

aws configservice put-configuration-aggregator \
  --configuration-aggregator-name org-wide \
  --organization-aggregation-source '{
    "RoleArn": "arn:aws:iam::444455556666:role/AWSConfigRoleForOrganizations",
    "AllAwsRegions": true
  }'

# Preguntar por lo que NO cumple, en todas las cuentas y Regiones a la vez.
aws configservice get-aggregate-compliance-details-by-config-rule \
  --configuration-aggregator-name org-wide \
  --config-rule-name s3-bucket-server-side-encryption-enabled \
  --account-id 111122223333 \
  --aws-region eu-west-1 \
  --compliance-type NON_COMPLIANT

AWS Audit Manager vs AWS Artifact (6.3.2)

RecopilaPara qué
Audit ManagerEvidencia continua de TU propia cuenta (config, logs, políticas)Preparar TUS auditorías, mapeado contra un framework (PCI-DSS, HIPAA...)
AWS ArtifactInformes de compliance de AWS COMO PROVEEDOR (SOC 2, ISO 27001)Demostrar que la infraestructura subyacente de AWS cumple esos estándares; también gestiona la aceptación de acuerdos como el BAA
Si vienes de Azure AWS Artifact ↔ Microsoft Service Trust Portal (informes de compliance del proveedor). Audit Manager ↔ Microsoft Purview Compliance Manager (recopilación de evidencia de tu propio entorno).

AWS Well-Architected Tool (6.3.3)

Evalúa una carga de trabajo frente a los 6 pilares del framework (incluido Security), identificando riesgos y generando un plan de mejora priorizado — normalmente vía un workshop estructurado con el equipo dueño de la carga de trabajo.

Si vienes de Azure Microsoft tiene un equivalente casi directo: la Azure Well-Architected Review, estructurada también en pilares (incluyendo Security). Uno de los mapeos más limpios del examen — incluso comparten filosofía de "framework de pilares + herramienta de autoevaluación".

Trampas típicas del examen

Los errores que más se repiten en este dominio. Si vas justo de tiempo antes del examen, repasa solo esto y el quiz.

La management account queda fuera de las SCP Ninguna SCP restringe a la management account de la organización. Por eso AWS recomienda no alojar cargas de trabajo en ella y usarla solo para gestionar la organización. Es de las trampas más repetidas del dominio.
Los tres tipos de control de Control Tower Preventivos (SCP): impiden que la acción ocurra. Detectivos (reglas de Config): avisan de lo que ya se desvió. Proactivos (hooks de CloudFormation): validan la plantilla antes de desplegar. Si una opción dice que un control detectivo "bloquea", se contradice a sí misma.
Config es regional y por cuenta Hay que habilitarlo donde estén los recursos: la cuenta de gestión no hereda el estado de las demás. Para la vista consolidada se usa un aggregator, y para aplicar el mismo conjunto de reglas en todas partes, conformance packs a nivel de organización.
Las tag policies no obligan a etiquetar Una tag policy estandariza claves y valores permitidos y señala lo que no cumple, pero por sí sola no impide crear un recurso sin etiquetas. Para exigirlo de verdad hace falta una SCP con una condición sobre aws:RequestTag.
Audit Manager no es Artifact AWS Artifact te entrega los informes de cumplimiento de AWS (SOC, ISO, PCI) para descargar. Audit Manager recoge evidencia continua de tu entorno frente a un marco. Uno documenta lo que hace AWS, el otro lo que haces tú.
Delegar administración no es dar acceso root El delegated administrator permite gestionar un servicio concreto (GuardDuty, Security Hub, Config…) desde una cuenta que no es la de gestión, sin repartir credenciales privilegiadas. Es el patrón recomendado frente a operar todo desde la management account.
