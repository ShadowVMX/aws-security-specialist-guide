Runbooks & AWS Systems Manager OpsCenter (2.1.1)

A response plan that only exists as a PDF is useless during a real incident — it has to be executable.

  • Systems Manager Automation runbooks: executable documents (SSM Documents) that automate response steps (isolating an instance, rotating a credential, capturing a snapshot) in a repeatable, audited way.
  • OpsCenter: centralizes "OpsItems" (incidents/problems) with context already linked in (affected resources, related alarms, executable runbooks) — saves the investigator from having to hop console to console gathering context manually.
  • Amazon SageMaker AI notebooks: explicitly called out as a forensic workbench — an isolated Jupyter environment for analyzing captured artifacts (memory dumps, logs) with reproducible scripts.

Preparation: minimizing blast radius & provisioning access (2.1.2)

Preparation happens BEFORE the incident. The exam treats it as its own phase, not an afterthought.

PracticeWhy it matters
Multi-account strategy + least privilegeLimits how far an attacker can get if a single workload is compromised.
Pre-provisioned, audited IR roleAvoids creating emergency permissions in a hurry (with the risk of over-granting) in the middle of a crisis.
Shield Advanced already contracted on critical resourcesDRT protection/support can't be improvised during an active DDoS attack.
Golden AMIs / IaC ready to goLets you rebuild quickly instead of "cleaning up" a compromised resource.
Plain-language example It's the difference between keeping a spare house key in a known drawer and having to call a locksmith at 3 AM because you got locked out. An "IR-Responder" IAM role with broad read-only permissions plus a handful of specific containment actions (modify SG, create snapshot), already created and tested, is the spare key. Creating that role IN THE MIDDLE of the incident is calling the locksmith — slower and with more room for error.

Testing the plan: Fault Injection Service & Resilience Hub (2.1.3)

ToolWhat it validates
Tabletop exerciseWhether the TEAM knows what to do and communicates well (discussion only, no touching real systems).
AWS Fault Injection Service (FIS)Whether the TECHNOLOGY actually responds: controlled failure experiments (AZ outage, latency, terminating instances) with automatic guardrails/stop conditions.
AWS Resilience HubWhether the architecture meets defined RTO/RPO objectives; identifies gaps and can orchestrate FIS experiments to validate it.
Coming from Azure AWS Fault Injection Service ↔ Azure Chaos Studio: a very direct mapping — both are managed chaos engineering services with predefined experiments and safety guardrails. Resilience Hub doesn't have as neatly packaged an equivalent in Azure — the closest thing would be combining Azure Monitor with manual reviews against the Azure Well-Architected Framework.

Automated remediation (2.1.4)

The standard pattern: finding → EventBridge → Lambda/Step Functions → containment action, without waiting for a human for initial containment.

EventBridge rule that triggers containment on a critical GuardDuty finding

aws events put-rule \
  --name "guardduty-critical-auto-contain" \
  --event-pattern '{
    "source": ["aws.guardduty"],
    "detail-type": ["GuardDuty Finding"],
    "detail": {"severity": [{"numeric": [">=", 7]}]}
  }' \
  --targets "Id"="1","Arn"="arn:aws:lambda:eu-west-1:111122223333:function:IsolateCompromisedInstance"

Automated forensics flow (inspired by the Automated Forensics Orchestrator for EC2)

Watch out — common exam trap The intuitive first reaction to a compromised instance is "shut it down now." That's the WRONG answer if there's forensic value at stake: powering off destroys RAM memory (running processes, active connections, in-memory keys) before you can capture it. The correct sequence is isolate at the NETWORK level first, capture evidence, and only THEN terminate the instance.

Validating findings before acting (2.2.3 — new in SCS-C03)

A skill added in this version of the exam: not every alert deserves the highest-impact response immediately.

  • Correlate the finding with other sources (VPC Flow Logs, CloudTrail, Detective) before escalating to a high-impact action (e.g. terminating a production resource).
  • Confirm the actual scope: which resources are REALLY affected, not just the one that generated the finding?
  • Rule out known false positives (e.g. an authorized vulnerability scan that GuardDuty may flag as suspicious if it isn't in the trusted IP list allowlist).

Amazon Detective & root cause analysis (2.2.5)

GuardDuty/Security Hub tell you WHAT happened. Detective helps reconstruct HOW it got to that point.

  • Automatically builds a graph of relationships between entities (IAM roles, instances, IPs) from CloudTrail, VPC Flow Logs, and GuardDuty findings — without you having to correlate it manually.
  • Retains up to 1 year of data for retrospective analysis, but only from when it was ENABLED — turn it on as part of preparation, don't wait for the incident.
  • It doesn't replace CloudTrail/Flow Logs: it CONSUMES them. If those sources weren't active, Detective won't have anything to correlate for that period either.
Coming from Azure The closest equivalent to Amazon Detective is the Investigation Graph in Microsoft Sentinel: both visualize relationships between entities (users, IPs, resources) over time to support root cause analysis, instead of forcing you to correlate isolated events manually.

Containment, eradication & recovery (2.2.4)

PhaseTypical action
ContainmentIsolate at the network level (quarantine SG), revoke/rotate compromised credentials, revoke active sessions (STS).
EradicationRemove the compromise vector (patch, close the misconfigured permission that allowed it).
RecoveryRebuild from a golden AMI/IaC (don't reuse the compromised resource); restore data from an IMMUTABLE backup that predates the compromise.
Plain-language example Facing ransomware that encrypted a database, restoring "yesterday's 11 PM" backup seems obvious — but if the attacker had already been inside for 3 days before triggering the encryption, that backup from yesterday ALREADY contains their backdoor. That's why the exam leans so hard on immutable backups (Vault Lock) with enough retention depth: you need to be able to go back further than "the most recent available backup," to a point verifiably before the compromise.

Controlled regional recovery

For availability incidents at the region level (not just a security compromise), Amazon Application Recovery Controller continuously verifies that the backup region is ready (readiness checks) and offers safe "routing controls" to execute failover without improvising under pressure.
