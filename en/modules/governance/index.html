The 4 types of organization policy (6.1.3)

SCP and RCP were already covered in depth in the IAM module. Here's the quick recap plus the two that were missing.

TypeControls
Service Control Policy (SCP)Ceiling on identity PERMISSIONS — which API actions an identity in the account can perform.
Resource Control Policy (RCP)Who can access RESOURCES, including external/anonymous principals.
Declarative PolicyForces a specific CONFIGURATION state (e.g. mandatory IMDSv2) — not an API allow/deny.
AI services opt-out policyControls whether AWS AI services can use content from your accounts to train/improve their models.

RCP that closes resource access from outside the organization

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SoloIdentidadesDeLaOrganizacion",
      "Effect": "Deny",
      "Principal": "*",
      "Action": ["s3:*", "sts:AssumeRole"],
      "Resource": "*",
      "Condition": {
        "StringNotEqualsIfExists": { "aws:PrincipalOrgID": "o-abc123" },
        "BoolIfExists": { "aws:PrincipalIsAWSService": "false" }
      }
    }
  ]
}

SCP that prevents disabling security controls

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "NoApagarLaSeguridad",
      "Effect": "Deny",
      "Action": [
        "cloudtrail:StopLogging",
        "cloudtrail:DeleteTrail",
        "guardduty:DeleteDetector",
        "guardduty:DisassociateFromMasterAccount",
        "config:DeleteConfigurationRecorder",
        "config:StopConfigurationRecorder",

      ],
      "Resource": "*",
      "Condition": {
        "ArnNotLike": {
          "aws:PrincipalARN": "arn:aws:iam::*:role/OrgSecurityBreakGlass"
        }
      }
    }
  ]
}

Delegated administrator (6.1.4)

Plain-language example Think of the management account as the bank's vault: it exists, it's critical, but nobody should be walking in and out of it every day. Designating the "Audit" account as delegated administrator for GuardDuty/Security Hub/Access Analyzer is like giving the security team the keys to the surveillance room (they see everything, they act on everything related to security) without giving them the keys to the vault itself.

Root user: MFA, break-glass & centralized management (6.1.5)

  • Break-glass procedure: a documented and audited process for EMERGENCY root access (hardware MFA under controlled custody), never used for normal operation.
  • Centralized root access management: lets the management account invoke certain root actions in member accounts without needing to recover passwords individually, reducing the number of actually usable root credentials.
  • MFA mandatory on ALL root accounts, verifiable centrally.
Coming from Azure "Break-glass" is practically the same term and concept as Microsoft Entra ID's emergency access accounts: accounts excluded from Conditional Access, with physically stored credentials, monitored with alerts if they're ever used. One of the most direct mappings (even in the colloquial name) in the whole exam.

Remove root credentials and act only when needed

# Habilitar la gestión centralizada del acceso root en la organización.
aws organizations enable-aws-service-access \
  --service-principal iam.amazonaws.com

aws iam enable-organizations-root-credentials-management

# A partir de aquí, una tarea que exige root se hace con una sesión acotada
# por una TaskPolicy administrada por AWS — no con credenciales permanentes.
aws sts assume-root \
  --target-principal 111122223333 \
  --task-policy-arn arn:aws:iam::aws:policy/root-task/S3UnlockBucketPolicy

Infrastructure as Code at scale (6.2.1)

ToolWhat it's for

CloudFormation GuardPolicy-as-code: CUSTOM business/security rules the template must satisfy before deployment (shift-left).

Deploying a StackSet across an entire OU (integrated with Organizations)

aws cloudformation create-stack-set \
  --stack-set-name "baseline-security-config" \
  --template-url "https://s3.eu-west-1.amazonaws.com/templates/baseline.yaml" \
  --permission-model SERVICE_MANAGED \
  --auto-deployment Enabled=true,RetainStacksOnAccountRemoval=false

Tagging strategy (6.2.2)

It's not just FinOps: it's the foundation for ABAC, conditional conformance packs, and fast incident response ("what is production?", "who is the owner?").

Actually requiring tags: the SCP that backs the tag policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "SinClasificacionNoSeCrea",
      "Effect": "Deny",
      "Action": ["ec2:RunInstances", "rds:CreateDBInstance"],
      "Resource": "*",
      "Condition": {
        "Null": { "aws:RequestTag/DataClassification": "true" }
      }
    }
  ]
}

AWS Firewall Manager (6.2.3)

Applies and MAINTAINS WAF, Shield Advanced, Security Groups, and Network Firewall policies centrally across the entire organization — even for accounts and resources created in the future, without repeated manual intervention.

Coming from Azure AWS Firewall Manager ↔ Azure Firewall Manager: an almost literal mapping, even in the name. Both centralize firewall/WAF policies at Management Group/Organization scale.

Sharing resources across accounts (6.2.4)

ServiceShares
AWS Resource Access Manager (RAM)Specific resources (subnets of a shared VPC, Transit Gateway, Firewall Manager rules) directly between accounts, without duplicating them.
AWS Service CatalogPRE-APPROVED IaC templates as self-service "products," giving teams autonomy without granting broad resource-creation permissions.
Coming from Azure AWS RAM resembles sharing a VNet via Azure Lighthouse / delegated resource management, though RAM's most common use case (sharing subnets between accounts, "shared VPC") is closer to a centrally-managed hub-spoke with VNet peering pattern than to Lighthouse itself — don't force the Lighthouse comparison beyond "delegation of management between tenants/accounts."

Config aggregators & automated remediation (6.3.1)

A Config Aggregator consolidates the compliance state of multiple accounts/regions into a single view. Standard response pattern:

Config detects → EventBridge → SNS (notifies) + Systems Manager Automation (remediates)

aws configservice put-remediation-configurations \
  --remediation-configurations '[{
    "ConfigRuleName": "s3-bucket-public-read-prohibited",
    "TargetType": "SSM_DOCUMENT",
    "TargetId": "AWSConfigRemediation-RemoveS3BucketPublicReadAccess",
    "Automatic": true,
    "MaximumAutomaticAttempts": 3
  }]'

Config aggregator across the whole organization

aws configservice put-configuration-aggregator \
  --configuration-aggregator-name org-wide \
  --organization-aggregation-source '{
    "RoleArn": "arn:aws:iam::444455556666:role/AWSConfigRoleForOrganizations",
    "AllAwsRegions": true
  }'

# Preguntar por lo que NO cumple, en todas las cuentas y Regiones a la vez.
aws configservice get-aggregate-compliance-details-by-config-rule \
  --configuration-aggregator-name org-wide \
  --config-rule-name s3-bucket-server-side-encryption-enabled \
  --account-id 111122223333 \
  --aws-region eu-west-1 \
  --compliance-type NON_COMPLIANT

AWS Audit Manager vs AWS Artifact (6.3.2)

CollectsWhat it's for
Audit ManagerContinuous evidence from YOUR OWN account (config, logs, policies)Preparing YOUR audits, mapped against a framework (PCI-DSS, HIPAA...)
AWS ArtifactAWS's OWN compliance reports as a provider (SOC 2, ISO 27001)Demonstrating that AWS's underlying infrastructure meets those standards; also manages acceptance of agreements like the BAA
Coming from Azure AWS Artifact ↔ Microsoft Service Trust Portal (provider compliance reports). Audit Manager ↔ Microsoft Purview Compliance Manager (evidence collection from your own environment).

AWS Well-Architected Tool (6.3.3)

Evaluates a workload against the framework's 6 pillars (including Security), identifying risks and generating a prioritized improvement plan — typically through a structured workshop with the team that owns the workload.

Coming from Azure Microsoft has an almost direct equivalent: the Azure Well-Architected Review, also structured around pillars (including Security). One of the cleanest mappings in the exam — they even share the "pillar framework + self-assessment tool" philosophy.

Classic exam traps

The mistakes that repeat most in this domain. If you're short on time before the exam, review just this and the quiz.

The management account is outside SCP reach No SCP restricts the organization's management account. That's why AWS recommends not running workloads in it and using it only to manage the organization. It's one of the domain's most repeated traps.
Control Tower's three control types Preventive (SCP): stop the action from happening. Detective (Config rules): flag what already drifted. Proactive (CloudFormation hooks): validate the template before deployment. If an option says a detective control "blocks", it contradicts itself.
Config is regional and per-account It must be enabled where the resources are: the management account inherits nothing from the others. For the consolidated view you use an aggregator, and to apply the same rule set everywhere, organization-level conformance packs.
Tag policies don't force tagging A tag policy standardizes allowed keys and values and flags what doesn't comply, but on its own it won't stop a resource being created untagged. To actually require it you need an SCP with a condition on aws:RequestTag.
Audit Manager is not Artifact AWS Artifact hands you AWS's own compliance reports (SOC, ISO, PCI) to download. Audit Manager continuously collects evidence about your environment against a framework. One documents what AWS does, the other what you do.
Delegating administration is not handing over root The delegated administrator lets you manage one specific service (GuardDuty, Security Hub, Config…) from an account that isn't the management one, without spreading privileged credentials. It's the recommended pattern versus operating everything from the management account.
