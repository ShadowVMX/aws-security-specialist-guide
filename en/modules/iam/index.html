Policy types in IAM

Everything in IAM revolves around JSON policy documents evaluated against three questions: who (Principal)? what action? on what resource?

TypeAttaches toKey exam notes
Identity-based (managed)Users, Groups, RolesAWS managed (predefined by AWS) or Customer managed (created by you). Reusable and versioned.
Identity-based (inline)A single User, Group, or Role1:1 relationship, not reusable. Useful only for very specific edge cases; poor practice at scale.
Resource-basedThe resource itself (S3, KMS, SQS, SNS, Lambda, Secrets Manager…)The only type that can specify a Principal from ANOTHER account directly, enabling cross-account access without AssumeRole.
Permission boundaryUsers or RolesGrants no permissions on its own; it sets the maximum ceiling. The effective permission is the intersection.
Organizations SCPAccounts / OUsGuardrail that limits identities WITHIN the organization. Never grants permissions by itself.
Organizations RCPAccounts / OUsGuardrail that limits access to RESOURCES, including external/anonymous principals. Complements SCPs.
Session policyPassed in when calling AssumeRole/GetFederationTokenJust like a boundary: it can only narrow, never widen, the role's permissions.
Exam tip If a question describes "I want to cap what a developer can do even though their role has broad permissions" → permission boundary. If it describes "I want a guardrail that applies to an entire OU no matter what policy each user has" → SCP (identities) or RCP (resources).

IAM policy evaluation order (updated with RCP, 2024+)

Step-by-step example Ana (a developer) tries to delete an object from the finance-reports bucket using s3:DeleteObject.

1. The request arrives: Principal = Ana, Action = s3:DeleteObject, Resource = the object.
2. Explicit Deny? The bucket policy for finance-reports has an explicit Deny for s3:DeleteObject except for the FinanceAdmin role. Ana isn't that role → immediate DENY, evaluation ends. It doesn't matter that her identity policy grants her s3:*: the explicit Deny in a third document (the bucket policy) still wins.

If that Deny didn't exist, we'd keep going: does her OU's SCP allow s3:DeleteObject? Does Ana have an explicit Allow in her identity policy? Does her permission boundary also allow it? Only if all FOUR questions come back green does the delete go through.

IAM Roles & AWS STS

A Role is an identity with permission policies that has NO permanent credentials: it is "assumed" and generates temporary credentials via AWS STS (Security Token Service).

STS APIWhen to use it
AssumeRoleGeneral case: an IAM User or Role (same account or cross-account) assumes another role.
AssumeRoleWithSAMLEnterprise federation with a SAML 2.0 IdP (ADFS, Okta, Azure AD/Entra ID) without IAM users.
AssumeRoleWithWebIdentityMobile/web apps with OIDC login (Google, Facebook, Amazon Cognito). In production, better done via Cognito Identity Pools.
GetFederationTokenLegacy federation to grant limited access to users without an IAM identity, using the calling user's own credentials.
GetSessionTokenTemporary credentials for an existing IAM User, typically to enforce MFA on API calls.
DecodeAuthorizationMessageDecodes the encoded error message when a call was denied (troubleshooting).

Trust policy (assume role policy document) for a role

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": { "AWS": "arn:aws:iam::111122223333:root" },
      "Action": "sts:AssumeRole",
      "Condition": {
        "StringEquals": { "sts:ExternalId": "unique-partner-id-2026" }
      }
    }
  ]
}

Assuming the role via AWS CLI

aws sts assume-role \
  --role-arn "arn:aws:iam::444455556666:role/CrossAccountAuditRole" \
  --role-session-name "juan-audit-session" \
  --external-id "unique-partner-id-2026" \
  --duration-seconds 3600
Watch out sts:ExternalId is mandatory when a third party (a SaaS provider, an external auditor) assumes your role, to mitigate the confused deputy problem. Always combine it with aws:SourceArn/aws:SourceAccount when the one assuming is an AWS service acting on behalf of another customer.

Amazon S3 presigned URLs — the other way to grant temporary access

The SCS-C03 exam guide groups STS and S3 presigned URLs under the same skill: "mechanisms for issuing temporary credentials." They are not the same thing, and the exam distinguishes when to use each:

  • A presigned URL doesn't generate new credentials: it signs a URL with the credentials of whoever generates it (user or role), delegating access to ONE action on ONE specific object for a limited time (up to 7 days with SigV4 and IAM Role credentials, or up to 12h if signed with a role's temporary credentials).
  • Ideal for letting a client without AWS credentials (a browser, an external app) upload or download a single S3 object, without ever exposing access keys or requiring it to assume a role.
  • If whoever generated the URL loses the underlying permission (their role/policy is revoked) before it expires, the URL stops working — it's still evaluated against IAM on every use.

Generating a presigned URL via CLI (expires in 300s)

aws s3 presign s3://reports-bucket/2026/audit-final.pdf --expires-in 300

Cross-account access & confused deputy

The most-tested pattern on the exam: a user in Account A needs to operate on resources in Account B.

Click any step of the diagram to see the detailed explanation.

Cross-account AssumeRole flow (requires outbound permission AND inbound trust policy)

Example: why ExternalId exists You hire "DataSync Corp" (a third-party SaaS) to back up your S3 bucket. You give them the ARN of a role in your account with a trust policy that trusts DataSync Corp's AWS account. Problem: DataSync Corp has hundreds of customers, and their generic trust policy could let them assume that role using the same account credentials for anyone. If another DataSync Corp customer (maliciously, or due to a misconfiguration on DataSync Corp's own side) manages to get the service to assume YOUR role instead of theirs, they access your data without you ever having granted it to them directly — that's the "confused deputy" (DataSync Corp is the "confused deputy"). By requiring a unique sts:ExternalId known only to you and DataSync Corp, your trust policy only trusts the exact account+ExternalId combination, closing that gap.
Coming from Azure The closest equivalent here is Azure Lighthouse: it lets a management tenant (e.g. an MSP) operate resources within your tenant without switching context. The important difference for the exam: in Azure Lighthouse the delegation is persistent and visible directly in the managing tenant's portal (there's no explicit "assume" on every operation); in AWS, cross-account access is always an explicit call to sts:AssumeRole that generates temporary, expiring credentials — a model actually closer to requesting a token for a Service Principal with permissions delegated in your tenant via Azure AD.

IAM Identity Center

Successor to AWS SSO. It's AWS's recommended way to manage multi-account human access in 2026, over creating individual IAM Users.

  • Permission Sets: permission templates (managed or customer policies + permission boundaries) defined once and assigned to accounts/groups. Identity Center automatically provisions the underlying IAM Roles in each account.
  • Identity source: can use Identity Center's internal directory, or federate with an external IdP (Okta, Azure AD/Entra ID, Google Workspace, Ping) via SAML/SCIM to sync users and groups automatically.
  • Built-in attribute-based access control (ABAC): Identity Center can pass user attributes (department, cost center) as session tags when assuming the permission set.
  • Replaces the old pattern of "one IAM User per person + long-lived credentials" — drastically reducing the risk of leaked access keys.
Coming from Azure
AzureAWSKey difference
Microsoft Entra ID (tenant)AWS Organization + IAM Identity CenterIn Azure the Entra ID tenant IS your central identity. In AWS these are two separate things: the Organization groups ACCOUNTS (closer to "subscriptions"), and Identity Center is the identity layer that connects on top of it.
Entra ID group + Azure RBAC role assignment (scope: subscription/RG)Group assigned to a Permission Set over one or more accountsConceptually almost identical: group + role + scope.
Enterprise Applications (federated SSO)Apps federated via SAML/OIDC in Identity CenterSame concept, different console.

Amazon Cognito & AWS Directory Service

Skill 4.1.1 explicitly groups IAM Identity Center, Cognito, and MFA as the three pieces for authenticating humans, applications, and systems. Identity Center covers human access to AWS accounts; Cognito covers end users of your own applications.

ComponentWhat it's forKey detail
Cognito User PoolsUser directory for YOUR application (sign-up/sign-in, MFA, email/SMS verification)Returns JSON Web Tokens (ID, Access, Refresh) after login. Does not grant AWS credentials by itself.
Cognito Identity PoolsExchanges an already-authenticated identity (from a User Pool, Google, SAML...) for temporary AWS credentialsThe recommended layer over AssumeRoleWithWebIdentity — it manages the exchange securely without exposing secrets on the client.
AWS Directory ServiceManaged Active Directory directories for on-prem/hybrid enterprise authentication3 modes: AWS Managed Microsoft AD (a real, managed AD, supports trusts), AD Connector (a proxy to an existing on-premises AD, without replicating data), and Simple AD (Samba-compatible, reduced functionality).
How to tell them apart on the exam "End users of my web/mobile app log in" → Cognito. "Company employees access the AWS console/CLI with their corporate account" → IAM Identity Center (possibly federated against AD via Directory Service). "I want to expose an existing on-premises AD to AWS services without migrating it" → AD Connector.
Coming from Azure Cognito User Pools is the equivalent of Azure AD B2C / Microsoft Entra External ID: identity management for customers/end users of YOUR application, separate from the corporate tenant. Cognito Identity Pools has no direct analog in Azure — the usual way there to grant an authenticated external user access to resources is through a token validated by your own backend, which then uses ITS OWN identity (Managed Identity or Service Principal) to touch the resources, rather than "swapping" the end user's token for cloud credentials the way Cognito Identity Pools does.

IAM Roles Anywhere

Extends IAM roles to workloads running OUTSIDE of AWS: on-premises servers, other cloud providers, edge devices.

  • Requires a trusted private CA (ACM Private CA or another CA registered as a trust anchor) that issues X.509 certificates to each server/workload.
  • The workload presents its certificate to the Roles Anywhere endpoint, which validates it and exchanges it for temporary AWS credentials via STS — the same principle as AssumeRoleWithSAML but with certificates instead of SAML assertions.
  • Removes the need for long-lived access keys manually distributed to servers outside AWS.

Authentication troubleshooting

Skill 4.1.3, explicit in the exam guide: knowing where to look when someone "can't log in" is just as testable as configuring it.

  • CloudTrail: the first place to check for a failed AssumeRole/ConsoleLogin event and its exact reason (errorCode, errorMessage) — includes attempts denied by trust policy, missing MFA, or an SCP.
  • Cognito: review Advanced Security Features logs and User Pool events (verification failures, throttling, Lambda triggers blocking login).
  • IAM Identity Center permission sets: an edited permission set doesn't auto-reprovision in accounts — it has to be reapplied, a common cause of "I removed the permission but they still have access" or the reverse.
  • AWS Directory Service: network connectivity issues (Security Groups, NACLs) between the VPC and on-premises DCs are the most common cause of AD Connector failures.

Permission boundaries, session policies & IAM paths

Both mechanisms share the same rule: they never widen permissions, only narrow them via intersection with the identity/resource policy.

Permission boundary — a developer can only touch S3 and DynamoDB, never IAM

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["s3:*", "dynamodb:*"],
      "Resource": "*"
    },
    {
      "Effect": "Deny",
      "Action": ["iam:*"],
      "Resource": "*"
    }
  ]
}
Typical exam use case "Allow developers to create their own IAM roles, but without letting them grant themselves admin permissions" → attach a mandatory permission boundary in the policy that grants them iam:CreateRole, using the iam:PermissionsBoundary condition.
Plain-language example — no direct Azure equivalent Imagine you give an intern the Contributor role over a resource group in Azure. If tomorrow someone (by mistake or maliciously) also assigns them the Owner role, there's no native Azure RBAC mechanism that says "no matter what role gets assigned afterward, this intern can NEVER exceed ceiling X." Every role assignment is independent. In AWS that structural ceiling does exist: if the intern has a permission boundary that only allows S3/DynamoDB, even if someone mistakenly attaches AdministratorAccess as their identity policy, their real permissions stay capped at S3/DynamoDB — the boundary always wins. That's why the exam asks about it so much: it's a genuinely different concept from "assigning a role with more or fewer permissions."

IAM paths — organizing and scoping identities by prefix

Every IAM User and Role has an optional path (default /) that's part of its ARN: arn:aws:iam::111122223333:role/division_abc/subdivision_xyz/my-role. Skill 4.2.1 lists it alongside resource policies and trust policies as an authorization control mechanism.

  • Useful for grouping identities by team/project and then writing administration policies that only allow managing roles/users under a specific path, using conditions like iam:ResourceTag or restricting the Resource with a wildcard over the path (arn:aws:iam::*:role/division_abc/*).
  • A typical exam scenario: delegating role creation to a platform team scoped only to their own path, combined with a mandatory permission boundary — a double least-privilege control.

ABAC & RBAC — attribute-based vs. role-based access control

RBAC (role-based) is the classic model: one policy per business role/function. ABAC (attribute-based) compares tags on the principal with tags on the resource — scaling without rewriting policies as the number of resources grows.

ABAC policy: access only to resources with the same "project" as the user

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": ["ec2:StartInstances", "ec2:StopInstances"],
      "Resource": "arn:aws:ec2:*:*:instance/*",
      "Condition": {
        "StringEquals": {
          "aws:ResourceTag/project": "${aws:PrincipalTag/project}"
        }
      }
    }
  ]
}
  • Requires enabling tag-based access control and consistently tagging both identities (via Identity Center session tags or IAM Role tags) and resources.
  • Ideal for multi-team environments where the number of resources keeps growing — avoids maintaining hundreds of specific policies.
Coming from Azure Azure also has ABAC, but with much narrower scope: in Azure, attribute-based role conditions are only supported on Blob Storage and a handful of specific resource types (e.g. "read-only access to blobs tagged Project=Finance"). In AWS, ABAC works across most services (EC2, S3, KMS, Secrets Manager...) because it's implemented directly as conditions within any IAM policy, rather than as a separate capability of one particular service.

Amazon Verified Permissions

Everything above (identity-based, resource-based, ABAC) authorizes access to the AWS API. Amazon Verified Permissions solves a different problem: fine-grained authorization inside YOUR OWN applications (can this user view this document? can they edit this order?), outside the AWS control plane.

  • A managed authorization engine based on Cedar, AWS's open-source policy language: readable policies like permit(principal == User::"ana", action == Action::"viewDocument", resource in Folder::"finance").
  • Integrates into your application code via SDK/API (IsAuthorized) — the app asks Verified Permissions on every request whether that specific action is allowed, instead of hardcoding authorization logic.
  • Supports RBAC and ABAC within the Cedar model itself, and integrates natively with Cognito to use the authenticated user's groups/attributes.
How to tell it apart on the exam If the question is about permissions on calls to the AWS API (S3, EC2, IAM...) → classic IAM policy. If it's about business logic inside your application ("which documents can this user of my SaaS see") → Amazon Verified Permissions.

Organization guardrails: SCP, RCP, and Declarative Policies

MechanismWhat it limitsApplies to
Service Control Policy (SCP)The maximum permission the account's IDENTITIES can use (even if IAM says yes, if the SCP doesn't allow it, it's denied)Accounts / OUs within the Organization
Resource Control Policy (RCP)Who can access the account's RESOURCES, including external and anonymous principals — closes the gap SCPs don't coverSupported resources (S3, STS, KMS, SQS, Secrets Manager…) in accounts / OUs
Declarative PoliciesEnforces a desired configuration state for specific service attributes (e.g. requiring IMDSv2, blocking public ports by default) — it's not API allow/deny, it's "this is how it must always be configured"Specific supported attributes, at account / OU level
How to tell them apart on the exam If the question says "we want no account to be able to disable EBS default encryption, no matter what" → Declarative Policy. If it says "we want no one in the organization to be able to use the eu-west-1 region" → SCP. If it says "we want no S3 bucket in the organization to be shareable with accounts outside the organization, even with bucket-level policy conditions" → RCP.
Watch out if you're coming from Azure — a naming trap "Service Control Policy" sounds like Azure Policy, but they are NOT the same thing. Azure Policy mainly audits/enforces the configuration of resources as they're created (e.g. "every storage account must require HTTPS") — that's actually much closer to AWS Declarative Policies or Config Rules. An SCP, by contrast, is a ceiling on IAM permissions (what actions an identity can execute), and its closest Azure equivalent is deny assignments (used in Blueprints/Landing Zones), which block actions at the Management Group level regardless of what RBAC role the user has been assigned. If you see "SCP" on the exam, think denied permissions, not configuration compliance.

IAM Access Analyzer & Policy Simulator

Skill 4.2.4 explicitly names both tools for analyzing authorization failures — they answer different questions.

  • External access findings: detects resources (buckets, roles, KMS keys, snapshots...) accessible from outside your "zone of trust" (account or organization). An analyzer is defined with the desired scope.
  • Unused access findings: identifies unused roles, unexercised permissions, and inactive access keys — direct support for the least-privilege principle.
  • Policy validation & custom policy checks: validates syntax and best practices as you write policies in the console/CLI, and even lets you check whether a policy change introduces new external access before deploying it (CheckNoNewAccess / CheckAccessNotGranted).

Listing external access findings via CLI

aws accessanalyzer list-findings-v2 \
  --analyzer-arn "arn:aws:access-analyzer:eu-west-1:111122223333:analyzer/org-analyzer" \
  --filter '{"findingType": {"eq": ["ExternalAccess"]}}'

IAM Policy Simulator

A distinct, complementary tool: instead of analyzing the account's real posture (like Access Analyzer), it simulates whether a specific policy would allow or deny a given action BEFORE any real change is applied — without generating real API calls or leaving a trace in CloudTrail.

IAM Policy SimulatorIAM Access Analyzer
Answers"Would this policy allow this specific action?""What EXTERNAL/UNUSED access exists right now in the account?"
When to use itBefore deploying/debugging a specific policyContinuous auditing of the account's real permission posture
Generates real trafficNoNo (analyzes policy metadata)

Simulating an action via CLI

aws iam simulate-principal-policy \
  --policy-source-arn "arn:aws:iam::111122223333:role/DevRole" \
  --action-names "s3:DeleteBucket" \
  --resource-arns "arn:aws:s3:::prod-critical-bucket"

Root user & MFA

  • Never use the root user for day-to-day tasks. Enable MFA (preferably FIDO2/hardware security key) and never generate access keys for root.
  • Centralized Root Access Management (Organizations, 2023+): lets you centrally manage member accounts' root credentials and invoke a scoped set of privileged root actions without repeating the password-recovery process account by account.
  • aws:MultiFactorAuthPresent condition to require MFA on API calls; combine it with aws:MultiFactorAuthAge to cap the maximum age of the MFA session.
  • IAM credential report (whole account) vs Access Advisor (per user/role, which services were used and when) — both key for periodic audits.

Requiring MFA for any action on EC2

{
  "Effect": "Deny",
  "Action": "ec2:*",
  "Resource": "*",
  "Condition": {
    "BoolIfExists": { "aws:MultiFactorAuthPresent": "false" }
  }
}
Coming from Azure Here the gap runs the opposite way from usual: in Azure, Conditional Access is a centralized engine that evaluates signals (location, user risk, device compliance...) and decides in one place whether to require MFA, block access, or force a managed device, applied uniformly across the whole tenant. AWS has no equivalent centralized engine: the aws:MultiFactorAuthPresent condition has to be added policy by policy (or centrally via SCP/RCP, but it's still a yes/no condition, not an adaptive risk engine). If an exam question sounds like "adaptive, risk-based conditional access policies," the correct answer probably combines several services (IAM + GuardDuty + Identity Center), not a single service equivalent to Conditional Access.
