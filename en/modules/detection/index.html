GuardDuty vs Macie vs Config vs Security Hub

Four services the exam deliberately conflates in wrong answers. Each one answers a different question.

ServiceQuestion it answersHow it works
GuardDuty"Is there anomalous behavior or an active threat?"ML + threat intelligence over CloudTrail, VPC Flow Logs, DNS logs, runtime monitoring — without manually enabling anything.
Macie"Where do I have sensitive data (PII) exposed or misplaced?"Discovery and classification of S3 content using ML and managed/custom patterns.
AWS Config"Does my configuration comply with rule X?" (e.g., encryption enabled)Evaluates the configuration STATE of resources against rules (Config Rules / Conformance Packs), with optional automatic remediation.
Security Hub"Give me EVERYTHING in a single dashboard, with compliance context"Aggregates findings from the above (+ third parties) and runs its own checks against CIS/PCI-DSS/AWS FSBP.
Exam tip If the question describes DATA content ("card numbers in a bucket") → Macie. If it describes BEHAVIOR/NETWORK ("API call from a Tor IP", "instance mining cryptocurrency") → GuardDuty. If it describes a resource's STATIC CONFIGURATION ("does this bucket have versioning enabled?") → Config. If it asks for a SINGLE DASHBOARD or talks about "security posture" in general → Security Hub.

Automating regular evaluations (1.1.5)

  • AWS Config Conformance Packs: a package of rules + remediations deployed centrally at the organization/OU level.
  • Security Hub: runs its compliance checks continuously and automatically, not as a one-off.
  • Systems Manager State Manager: applies and maintains a desired configuration state on instances (e.g., "the CloudWatch agent must always be running"), automatically correcting drift.

Log sources & logging architecture (1.2.1 / 1.2.2)

Identifying WHAT to log matters as much as HOW to centralize it.

SourceWhat it captures
CloudTrailAPI calls (management events: who did what; optional data events: operations on individual S3 objects/Lambda functions).
CloudWatch LogsApplication/system logs sent by the CloudWatch Agent, Lambda, containers, etc.
VPC Flow LogsNetwork connection metadata (see detail below).
Route 53 Resolver query logsDNS queries resolved from within the VPC.

Create a centralized organization trail via CLI (from the management account)

aws cloudtrail create-trail \
  --name "org-security-trail" \
  --s3-bucket-name "central-logging-account-cloudtrail" \
  --is-organization-trail \
  --is-multi-region-trail \
  --enable-log-file-validation
Plain-language example Imagine your production account gets compromised and the attacker obtains admin credentials. If that account's CloudTrail writes to an S3 bucket IN THE SAME ACCOUNT, the attacker can erase the trail of their own actions (s3:DeleteObject on the logs). But if the logs instead travel to a separate logging account where not even the compromised role has s3:DeleteObject, the evidence survives intact — account separation isn't bureaucracy, it's an active defense.

{
  "Version": "2012-10-17",

Create an organization trail that also captures S3 data events

aws cloudtrail create-trail \
  --name org-security-trail \
  --s3-bucket-name central-security-logs-111122223333 \
  --is-organization-trail \
  --is-multi-region-trail \
  --kms-key-id alias/cloudtrail-cmk

# Los data events NO se capturan por defecto: hay que pedirlos.
aws cloudtrail put-event-selectors \
  --trail-name org-security-trail \
  --advanced-event-selectors '[
    {
      "Name": "Lecturas y escrituras de objetos S3",
      "FieldSelectors": [
        { "Field": "eventCategory", "Equals": ["Data"] },
        { "Field": "resources.type", "Equals": ["AWS::S3::Object"] }
      ]
    }
  ]'

aws cloudtrail start-logging --name org-security-trail

Amazon Security Lake & OCSF (1.2.3)

  • Ingests, normalizes (to OCSF), and partitions logs from multiple AWS accounts/sources and compatible third parties into a managed data lake (built on S3, in your own account).
  • Eliminates the manual ETL work you'd need to correlate completely different log formats with a single query.
  • Integrates natively with Athena, OpenSearch, and third-party SIEMs that already speak OCSF.

Analyze, normalize & correlate (1.2.4 / 1.2.5)

Athena query: find denied calls in CloudTrail

SELECT eventtime,
       useridentity.arn      AS principal,
       eventsource,
       eventname,
       errorcode,
       sourceipaddress
FROM   cloudtrail_logs
WHERE  errorcode IN ('AccessDenied', 'UnauthorizedOperation')
  AND  eventtime > '2026-08-01T00:00:00Z'
ORDER  BY eventtime DESC
LIMIT  100;

VPC Flow Logs & Route 53 Resolver logs (1.2.6)

Key distinction VPC Flow Logs = WHO connected to WHOM (IP metadata, not content). Route 53 Resolver logs = WHAT DOMAIN was resolved before that connection. A typical DNS-tunneling exfiltration attack can go unnoticed in Flow Logs (DNS traffic looks normal in volume) but shows up clearly in the Resolver logs by analyzing the unusual ENTROPY/length of the subqueries.

Troubleshooting broken logging (1.3.1 / 1.3.2)

A very common question pattern: "the log group is empty, why?" — it's almost always the same two causes.

SymptomMost common causes
CloudWatch Agent running but no logsAgent configuration pointed at the wrong place (incorrect paths/log group) or insufficient IAM permissions on the Instance Profile.
Lambda executes but produces no logsExecution role missing logs:CreateLogStream/logs:PutLogEvents (missing the AWSLambdaBasicExecutionRole managed policy).
API Gateway missing request/response detailData trace logging isn't explicitly enabled at the stage level (default execution logging doesn't include the body).
CloudFront missing recent logsConfusing Standard logs (delayed, to S3) with Real-time logs (Kinesis, seconds) — check which one is actually configured.

Classic exam traps

The mistakes that repeat most in this domain. If you're short on time before the exam, review just this and the quiz.

Management events are not data events CloudTrail logs only management events by default (control plane: CreateBucket, PutBucketPolicy). Who downloaded a specific object is a data event, off by default and needing explicit enabling. If the stem says "we can't see who accessed the object", the answer is nearly always to enable data events.
GuardDuty doesn't need you to enable its sources GuardDuty reads CloudTrail, VPC Flow Logs and DNS logs independently, through a service-linked role. You don't need to enable or pay for those logs for GuardDuty to work. Any option saying "first enable VPC Flow Logs so GuardDuty can analyze them" is a distractor.
The four services that always get confused GuardDuty detects threats and malicious behavior. Inspector assesses vulnerabilities (CVEs) in instances, containers and Lambda. Macie discovers sensitive data in S3. Config evaluates resource configuration state. None does another's job, and the exam swaps them constantly.
Multi-account and multi-Region are separate axes In Security Hub, GuardDuty or Config, the delegated administrator solves the multi-account view and Region aggregation solves the multi-Region one. They are two separate settings: if the question asks for both, both answers are needed.
Logs never appear retroactively Extending retention, creating a new trail or enabling a source does not generate events that weren't captured at the time. If the incident already happened and logging was misconfigured, that evidence doesn't exist. Any option promising to recover past events is false.
VPC Flow Logs don't see content They record connection metadata (IPs, ports, protocol, bytes, accept/reject), never the payload. If the question needs to know what was transferred, Flow Logs aren't enough. They also skip some traffic, such as that to the Amazon DNS server or 169.254.169.254.
