Envelope encryption — the concept tested most

Envelope encryption: KMS never sees your data, only the data key

Coming from Azure Azure Key Vault also supports an envelope encryption pattern (using WrapKey/UnwrapKey), conceptually identical. The organizational difference: Azure Key Vault is ONE service that stores keys, secrets, AND certificates together. AWS spreads that same functionality across three distinct services: KMS (encryption keys), Secrets Manager (credentials/secrets), and ACM (certificates) — each with its own console, pricing, and API. Mentally, "Key Vault" ≈ "KMS + Secrets Manager + ACM" combined.

Inter-resource encryption (5.1.3 — new in SCS-C03)

A skill added in the current version of the exam: encrypting traffic BETWEEN nodes of the same distributed service, not just client↔service.

  • Amazon EMR: "in-transit encryption" in the cluster's Security Configuration encrypts traffic between nodes (including Spark shuffle) with TLS.
  • Amazon EKS: inter-node encryption typically goes through a service mesh (App Mesh, Istio) or a CNI with encryption support — it's not automatic by default in the data plane.
  • Amazon SageMaker AI: "inter-container traffic encryption" encrypts communication between the containers of a distributed training job.
  • Nitro encryption: on EC2 instances running on the Nitro System, traffic between Nitro instances (and local memory) is automatically encrypted at the infrastructure level, with no client configuration.
Plain-language example Encrypting your S3 bucket with SSE-KMS protects data AT REST on disk. But if you have a 20-node EMR cluster processing that data and shuffling intermediate results BETWEEN those 20 nodes, that internal traffic travels unencrypted unless you explicitly enable "in-transit encryption" in the Security Configuration — an easy point to miss, because "everything is already encrypted" (at rest) doesn't mean "all traffic is encrypted" (in transit, even internal traffic).

Data integrity (5.2.2)

  • S3 Object Lock: WORM (Write Once Read Many) at the object level. Governance mode (bypassable with a special permission) vs Compliance mode (immutable, not even root can bypass it).
  • S3 Glacier Vault Lock: a retention policy that, once confirmed ("locked"), is permanent and immutable — useful for verifiable regulatory compliance (SEC 17a-4, etc.).
  • S3 Versioning (+ MFA Delete): keeps every version of an object; MFA Delete requires an additional MFA code to delete versions or disable versioning.
  • AWS Signer: digital code signing (Lambda, containers, IoT firmware) to verify it hasn't been tampered with.
  • CloudTrail file validation: each log file includes a digitally signed hash to detect later tampering with the logs.

Configure Object Lock in Compliance mode via CLI

aws s3api put-object-retention \
  --bucket "regulated-records" \
  --key "contracts/2026-report.pdf" \
  --retention '{"Mode":"COMPLIANCE","RetainUntilDate":"2033-01-01T00:00:00Z"}'
Plain-language example Governance mode is like a "do not touch except in an emergency with special authorization" — an administrator with the s3:BypassGovernanceRetention permission can bypass it if truly necessary. Compliance mode is a lock with no key: not even the AWS account owner can open it before the set date. Use it only when regulation truly requires it, because there's no going back.

Lifecycle & retention (5.2.3)

  • S3 Lifecycle policies: transition rules (moving to a different storage class by age) and expiration rules (automatic deletion after N days).
  • Amazon EFS Lifecycle Management: automatically moves infrequently accessed files to EFS Infrequent Access.
  • Amazon FSx for Lustre backup policies: automatic scheduled snapshots of the file system.

The piece WITHOUT a direct equivalent that gets asked about a lot is AWS Backup Vault Lock: Azure Backup has "immutable vaults," conceptually similar, but on the AWS exam what matters is the Governance-like vs Compliance-like nuance within Vault Lock itself (compliance mode = irreversible, not even by AWS Support).

AWS Secrets Manager (5.3.1)

Managing and rotating credentials and secrets — the piece that most distinguishes Secrets Manager from simply "storing an encrypted value."

  • Native automatic rotation with built-in Lambda functions for RDS, Aurora, Redshift, and DocumentDB: it rotates the credential AND updates it in the database in the same cycle, with no downtime if configured correctly (alternating two-user rotation).
  • For other secrets (third-party API keys, tokens), you can write your own rotation Lambda function following the 4 standard phases: createSecret, setSecret, testSecret, finishSecret.
  • Native integration with IAM (secret resource policies) and KMS (encryption at rest).

Rotate an RDS secret every 30 days via CLI

aws secretsmanager rotate-secret \
  --secret-id "prod/rds/app-db" \
  --rotation-lambda-arn "arn:aws:lambda:eu-west-1:111122223333:function:SecretsManagerRDSRotation" \
  --rotation-rules '{"AutomaticallyAfterDays": 30}'
Coming from Azure Azure Key Vault Secrets covers encrypted storage, but it doesn't come with built-in automatic rotation for databases the way Secrets Manager does — in Azure you typically need Event Grid + custom Azure Functions to replicate that flow. It's a real difference in "included features," not just naming.

Imported key material & External Key Store (5.3.2 / 5.3.3)

See also the decision tree above. The nuance tested most here: the practical differences from a key generated by AWS.

Generated by AWSImported material (BYOK)
Automatic rotationYes (optional, annual)No — must be re-imported manually
Configurable expirationNoYes, optional (or "never expire")
Source of the materialGenerated inside AWS's HSMGenerated by you, imported via a public RSA wrapping key
If the material is deletedN/AThe key becomes immediately unusable (useful as a "kill switch")
Coming from Azure Azure Key Vault also supports BYOK (importing keys generated outside, even HSM-protected via a validated transfer package). The concept is equivalent. Where AWS goes a step further is External Key Store (XKS): the material NEVER enters AWS at any point, not even during import — Azure has no direct equivalent that strict (the closest would be a BYOK integration managed entirely outside via Managed HSM with your own access control, but XKS's "external proxy for every cryptographic operation" model is more AWS-specific).

Sensitive data masking (5.3.4 — new in SCS-C03)

Masking sensitive data that shows up where it shouldn't, without blocking the log/message flow entirely.

  • CloudWatch Logs data protection policies: detect sensitive data types (credit card numbers, SSNs, AWS access keys, or custom regex-based detectors) and mask the value in views/queries. Only principals with logs:Unmask see the real value.
  • Amazon SNS message data protection: the same idea applied to SNS messages — detects and masks (or blocks) sensitive data before the message reaches subscribers.

Data protection policy on a log group (excerpt)

{
  "Name": "mask-pii-policy",
  "Statement": [
    {
      "Sid": "audit-and-mask-credit-cards",
      "DataIdentifier": ["arn:aws:dataprotection::aws:data-identifier/CreditCardNumber"],
      "Operation": {
        "Audit": { "FindingsDestination": {} },
        "Deidentify": { "MaskConfig": {} }
      }
    }
  ]
}

Multi-Region certificates & keys (5.3.5)

ServiceWhat it's for
ACM (public)Free, publicly trusted TLS certificates with automatic renewal. For verifiable public domains.
AWS Private CAYour own private CA hierarchy: internal certificates for mTLS between microservices, IoT, IAM Roles Anywhere. Trusted only where you distribute the root certificate. Cost per active CA.
KMS Multi-Region keysReplicas that share the SAME cryptographic material across regions — encrypt in one region, decrypt in another without re-encrypting. Different from independently creating identical keys in each region (those would have distinct, incompatible material).
Watch out if you're coming from Azure Azure Key Vault is a regional resource: to get multi-region high availability for your keys, you manually replicate the entire Key Vault (or use Managed HSM with its own mechanism). AWS KMS Multi-Region keys are conceptually different: they aren't "the same service replicated" — they're replicas of ONE key with shared material managed natively by KMS (ReplicateKey), with different Key IDs per region but cryptographically interchangeable. Don't assume it's "the same thing under a different name."
